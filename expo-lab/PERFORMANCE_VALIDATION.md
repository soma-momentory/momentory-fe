# Expo Design Lab 캡처 목록 성능 검증

2026-10-14, iPhone Air 시뮬레이터(iOS 26.5, Expo Go SDK 57)와 macOS Chrome 155 헤드리스에서 측정했다. 운영 앱과 Vite Lab은 변경하지 않았다.

## 구조와 캐싱

- 변경 전에는 `ScrollView`가 38개 카드와 1080×2340px PNG 원본 38장을 한 번에 마운트했다. React Native `Image`의 플랫폼 기본 캐시를 사용하며 별도 프리페치나 캐시 제한은 없었다.
- 변경 후 갤러리는 `FlatList`의 고정 높이 행과 `getItemLayout`을 사용한다. 7개 그룹 제목은 행으로 유지하고, 화면 너비에 따라 카드를 한 행에 1–3개 배치한다. `initialNumToRender=3`, `maxToRenderPerBatch=4`, `windowSize=5`로 화면 밖 행의 이미지 마운트를 제한한다. 첫 배치는 목록 상단 재진입을 위해 남을 수 있고, 플랫폼 이미지 캐시의 해제 시점은 보장하지 않는다.
- 갤러리 이미지는 원본에서 가로 540px로 비례 축소한 PNG를 사용한다. 비교 화면은 선택한 화면의 1080px 원본만 사용한다. 원본 38장은 바이트 단위로 변경하지 않았다. 원본은 압축 23.10MiB·RGBA 전체 366.34MiB, 축소본은 압축 8.45MiB·RGBA 전체 91.58MiB다. RGBA 수치는 모든 이미지가 완전히 디코딩될 때의 계산값이지 관측 메모리가 아니다.
- 로컬 이미지의 실제 디스크·메모리 캐싱은 React Native와 브라우저에 맡긴다. 이 변경은 이미지 파일 크기와 동시 마운트 수를 줄이며, 이미 로드한 이미지가 즉시 메모리에서 제거된다고 가정하지 않는다.

축소본은 `assets/current-app-thumbnails/`에 커밋한다. macOS에서 원본 캡처를 갱신한 경우 `node expo-lab/scripts/generate-capture-thumbnails.mjs`로 다시 생성한다. 이 스크립트는 `sips`를 사용하고 `assets/current-app/`을 쓰지 않는다. 다른 OS와 CI에서는 생성 단계를 실행하지 않아도 된다.

## 전후 측정

웹은 새로운 Chrome 프로필에서 800×600px 창으로 `#atlas?device=390`을 열었다. 목록 준비 시점의 DOM/이미지 수와 Chrome Performance의 JS 힙을 기록하고, 내부 스크롤 영역을 `requestAnimationFrame` 90회에 걸쳐 상단에서 하단까지 이동했다. 개발 서버와 헤드리스 브라우저의 단일 실행 표본이므로 FPS나 실제 기기 체감 성능을 대표하지 않는다.

| 항목                              |         변경 전 |         변경 후 |
| --------------------------------- | --------------: | --------------: |
| 목록 준비 시 마운트된 캡처 이미지 |       38장 원본 |      2장 축소본 |
| 90프레임 하단 이동 후 이미지      |       38장 원본 |      8장 축소본 |
| 준비 시 이미지 원본 픽셀 합계     |      96,033,600 |       1,263,600 |
| Chrome DOM 노드 / JS 힙           | 834개 / 8.77MiB | 187개 / 6.04MiB |
| 90프레임 스크롤 평균 간격         |          16.7ms |          16.7ms |
| 33ms 초과 프레임                  |             0회 |             0회 |
| 90프레임 소요 시간                |       1,488.5ms |       1,497.7ms |

**스크롤 프레임 지표에서는 개선이 측정되지 않았다.** 기준선도 이 헤드리스 테스트에서 33ms 초과 프레임이 없었다. DOM·이미지 동시 렌더링 수는 감소했으나, 실제 손가락 스크롤의 프레임 시간은 별도 측정이 필요하다.

iOS는 같은 iPhone Air 시뮬레이터에서 Expo Go를 새로 실행해 목록 진입 후와 38개 화면의 비교 진입·복귀 후 프로세스 RSS를 `ps`로 읽었다. 조작은 실행 중인 React Native 버튼 콜백과 `FlatList.scrollToIndex`를 호출한 것으로, 실제 터치 제스처가 아니다.

| Expo Go 전체 프로세스 RSS |     변경 전 |   변경 후 |
| ------------------------- | ----------: | --------: |
| 목록 진입 후              |   약 911MiB | 약 520MiB |
| 38개 화면 왕복 후         | 약 1,107MiB | 약 613MiB |

RSS에는 Expo Go 자체, 개발 모드, 캐시와 시뮬레이터의 다른 비용이 포함된다. 두 실행의 절대값만으로 이미지 메모리 절감량이나 누수 해소를 증명할 수 없다. 다만 같은 시뮬레이터 조건에서 동시 이미지 수 감소와 함께 RSS 감소가 관찰됐다.

## 기능·플랫폼 확인과 남은 위험

- 웹에서 38개 비교 URL을 모두 열어 선택 캡처가 1080px 원본이고 미등록 시안은 대기 상태인지 확인했다. 그룹 딥링크, 화면 선택, 홈 상태·기기 전환, 브라우저 뒤로가기를 확인했다. 375·390·402·430px 뷰포트에서 카드가 가로로 잘리지 않고 갤러리에 540px 축소본이 쓰이는 것을 확인했다.
- iOS에서는 첫 화면 레이아웃을 캡처하고, 실행 중인 React Native 콜백으로 38개 카드의 비교 진입·복귀와 그룹·홈 상태·기기 전환을 확인했다. Expo Go 첫 실행 안내창과 Simulator GUI 부재로 실제 터치·스크롤 성능은 확인하지 못했다.
- Android SDK·에뮬레이터가 이 환경에 없어 Android 실제 렌더링과 메모리는 미검증이다. 번들 내보내기는 별도 확인한다.
- 축소본 8.45MiB가 Lab 패키지에 추가된다. 저사양 실기기에서 빠른 스크롤 시 빈 행, 이미지 로드 지연, 캐시 잔류와 메모리 경고를 확인해야 한다. Chrome 헤드리스 수치로 이를 대체하지 않는다.
