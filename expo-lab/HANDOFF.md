# Lab 시안 → 코드 반영은 AI 가 한다

> **정본.** Expo Lab 에서 만든 디자인 시안을 앱 코드로 옮기는 규칙은 이 문서 하나다(2026-11-02 사용자 결정).
> 스킬 `momentory-lab-handoff`(`.claude/skills/` · `.agents/skills/`)는 이 문서를 따라 움직이는 손잡이일 뿐이다.

## 나누는 일

| 누가                         | 무엇을                                                                                                                                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **사람** (Lab)               | 시안을 만들고 · 참고 시안 이미지를 넣어 겹쳐 보며 · 값을 맞추고 · A/B 로 확인한 뒤 **「AI에게 넘기기」** 로 파일을 내보낸다. 값으로 못 맞춘 차이는 메모에 적는다(「카드 사이 간격이 시안보다 넓다」 같은 말이면 된다). |
| **AI** (Claude Code · Codex) | 그 파일을 근거로 코드를 고치고 · 검사를 돌리고 · Lab 에서 다시 확인하고 · PR 을 올린다. **머지는 사람이 결과를 보고 승인한 뒤에만.**                                                                                   |

사람이 `design:apply*` 명령을 직접 칠 일은 없다고 보고 짠 규칙이다. 명령은 AI 가 쓰는 도구로 남긴다.

## 넘기는 파일 — `momentory-lab-handoff@1`

Lab 디자인 편집기의 「내보내기 · 코드 반영 → AI에게 넘기기」가 브라우저 다운로드 폴더에
`momentory-handoff-<시안이름>-<YYYYMMDD-HHmm>.json` 으로 내려 준다. 사용자가 경로를 말하지 않으면
AI 는 **다운로드 폴더(`~/Downloads`)에서 가장 최근의 `momentory-handoff-*.json`** 을 찾고, 어느 파일을 읽었는지 먼저 말한다.

```jsonc
{
  "format": "momentory-lab-handoff@1",
  "createdAt": "2026-11-02T21:30:00+09:00",
  "draft": { "id": "…", "name": "버튼 둥글게" },
  "request": "사용자가 적은 메모 — 값으로 못 맞춘 차이 · 의도", // 비어 있을 수 있다
  "tokens": [
    // 공통 값(src/design/ds) — 키는 export 경로를 점으로 이은 것
    { "key": "primary.heavy", "label": "주 버튼 면", "before": "#56755F", "after": "#4E6B57" },
  ],
  "studio": [
    // 화면별 값(src/design/studioApproved.json)
    {
      "key": "home.hero.borderRadius",
      "label": "홈 히어로 카드 · 모서리",
      "before": 16,
      "after": 22,
    },
    // 탭 배경(「탭 배경 바꿔 보기」 · src/design/tabBackgrounds.ts 의 tabBackgroundByTab) — 값은 배경 id
    {
      "key": "tabBackground.쉼터",
      "label": "쉼터 탭 배경",
      "before": "soft-olive",
      "after": "warm-ivory",
    },
  ],
  "screens": [
    // 시안을 본 화면 · 참고 시안 이미지 · 화면별 메모
    {
      "route": "/home",
      "note": "…",
      "reference": {
        "name": "home-v3.png",
        "dataUrl": "data:image/png;base64,…",
        "align": { "scale": 0.333, "offsetX": 0, "offsetY": 0 },
      },
    },
  ],
  "lab": { "platform": "ios", "deviceId": "iphone-16", "datasetId": "normal" },
}
```

`dataUrl` 은 크다 — 파일 전체를 출력하지 말고 필요한 필드만 읽는다. 참고 이미지는 임시 폴더에 풀어서 본다.

두 반영 스크립트는 이 파일을 그대로 받는다(`design:apply-tokens` 는 `tokens`, `design:apply` 는 `studio`).
`studio` 의 **`tabBackground.<탭>`**(홈 · 쉼터 · 보관함 · 리포트 · 마이)은 `design:apply` 가 `src/design/tabBackgrounds.ts` 의
`tabBackgroundByTab` 리터럴로 옮긴다 — 값은 같은 파일 `tabBackgroundAssets` 에 **이미 있는 배경 id** 만 받고, 모르는 id · 탭이
하나라도 있으면 아무 파일도 쓰지 않는다. 새 배경 그림이 필요하다는 메모면 「이미지 넣기」 절차로 그림을 넣고
`tabBackgroundAssets` 에 먼저 등록한 뒤 고른다.

## AI 의 절차

1. **읽고 요약해 확인받는다.** 시안 이름 · 바뀌는 값 목록(전 → 후) · 화면별 메모 · 참고 이미지 유무를 짧게 정리해 보여 준다.
   값으로 안 되는 요청(배치 · 구조 · 새 요소)은 따로 묶어 「코드 작업이 필요한 것」으로 알린다. 범위가 크면 이 단계에서 진행 여부를 묻는다.
2. **브랜치.** main 이면 `design/<시안이름>` 같은 브랜치를 먼저 만든다(`docs/CONTRIBUTING.md`).
3. **값 반영 — 도구를 먼저 쓴다.**
   ```bash
   npm run design:apply-tokens -- <파일>          # diff 만 — 결과를 읽는다
   npm run design:apply-tokens -- <파일> --write  # src/design/ds/*.ts
   npm run design:apply -- <파일>                 # 화면별 값 diff
   npm run design:apply -- <파일> --write         # src/design/studioApproved.json
   ```
   스크립트가 거절한 키(계산된 값 · 배열 · 모듈 맨 위 단독 값 · 두 파일에 정의된 값)는 **원래 정의를 찾아 손으로** 고친다 — 예: `withAlpha(primary.normal, …)` 로 계산되는 색이면 원본 토큰이나 계산식을 고친다. 바꾼 이유를 커밋 메시지에 적는다.
4. **구조 차이 — 코드로.** 참고 이미지와 메모를 근거로 화면 코드를 고친다. 이때도 저장소 규칙이 이긴다:
   `docs/DESIGN.md` 우선(N0·N6) · 색은 `src/design/ds/` 에 **이름을 먼저 만들고** 쓴다(hex 하드코딩 금지) · 선택 상태를 색만으로 표시하지 않는다 ·
   오류는 한 줄로 · 숫자로 압박하지 않는다 · 폰트는 파일 이름으로 (`CLAUDE.md` 「자주 어기게 되는 것」). 시안이 이 규칙과 부딪히면 **고치지 말고** 사용자에게 부딪히는 점을 말한다.
5. **디자인 정본을 함께 고친다.** 토큰 값 · 규칙이 바뀌면 `docs/DESIGN.md` 의 해당 값도 고친다(정본이 둘로 갈라지지 않게).
   대비 보정 자리(`PLAN.md` A-5 · `ds/color.ts` 머리말)를 건드리면 그 표도 갱신한다.
6. **검사.** `npm run typecheck` · `npm run lint` · `npm run format:check` · `npm run test`(대비 테스트 `src/design/ds/__tests__/contrast.test.ts` 포함).
   대비 테스트가 깨지면 값을 억지로 바꾸지 말고 사용자에게 「이 색은 글자 대비(WCAG AA)를 못 넘는다 — 후보 둘」로 되묻는다.
7. **Lab 에서 다시 본다 — `momentory-lab-verify` 로 바뀐 화면을 전 · 후 비교한다(기기 · 테스트 데이터 · 글씨 크기).**
   스크립트 `expo-lab/scripts/lab-verify.mjs` 가 main 을 띄운 Lab(전)과 고친 코드를 띄운 Lab(후)에서 바뀐 라우트를 같은 조건으로 찍고,
   화소 차이와 배치 문제(가로 넘침 · 글자 잘림 · 탭바/안전 영역 가림 · 콘솔 오류 · 실패한 요청)를 `report.html` · `report.json` 으로 낸다.
   AI 는 보고서와 **그림을 직접 보고** 의도한 변경 · 의도하지 않은 변경 · 새로 생긴 문제를 나눠 보고한다. 사용자의 8085 Lab 은 읽기만 한다.
   참고 이미지와의 겹쳐 보기 · 차이 보기는 지금처럼 셸에서 **A(승인본)** 로 한다 — 시안 프레임에 같은 값이 남아 있으면 비교가 흐려진다.
8. **PR.** `.github/PULL_REQUEST_TEMPLATE.md` 형식. 「주요 변경」에 값 전 → 후 표, 「확인 방법」에 Lab 주소(라우트 · 기기 · 데이터 세트), 「스크린샷」에 전 · 후 —
   절차 7 이 만든 `pr-screenshots.md` 조각을 쓴다(그림은 로컬 경로라 PR 편집창에 끌어 넣어 올린다 · 저장소에 커밋하지 않는다).
   **머지하지 않는다** — 사용자가 확인하고 승인한 뒤에만.

## Lab 에서 바로 맡길 때 (「AI에게 맡기기」 · 작업 공간)

Lab 패널에서 지시하면 서버가 **그 화면용 작업 공간**(저장소 바깥 git worktree + `lab/…` 브랜치 + 미리보기 Lab)을
첫 지시 때 만들고, 그 폴더에서 AI 를 돌린다. 이때는 위 절차를 이렇게 바꾼다.

- 1(확인받기)은 **질문하지 않고 요약을 출력으로 남기는 것**으로 대신한다. 규칙과 부딪히거나 값으로 안 되는 큰 구조 변경은 하지 말고 보고만 한다.
- 2(브랜치)는 이미 있다 — 새로 만들지 않는다.
- 7(Lab 확인)은 생략 — 사용자가 미리보기에서 본다. 전 · 후 비교 보고서가 필요하면 **Lab 실행기가 AI 가 끝난 뒤**
  `node expo-lab/scripts/lab-verify.mjs --before <main Lab> --after <미리보기 주소> --changed --repo <작업 공간>` 을 돌려 붙일 수 있다(실행기 몫 — AI 가 부르지 않는다).
- 8 대신 **커밋 · push · PR 을 하지 않는다.** 끝에 `COMMIT_MESSAGE:` 블록(한국어 `type: 문장형` + 본문 · Co-Authored-By 없음)과
  `PR_BODY:` 블록(`.github/PULL_REQUEST_TEMPLATE.md` 형식)을 출력한다. 사용자가 Lab 의 「수정 저장(커밋)」 · 「검토 요청 올리기(PR)」를 누른다.

## 새 화면 만들기

Lab 의 「＋ 새 화면 만들기」로 맡기면 넘어오는 것: 화면 이름 · 들어갈 곳(묶음) · 어떤 화면인지 설명 · (선택) 참고 시안 이미지.
위 절차에 더해 —

1. **자리를 정한다.** 들어갈 묶음에 맞춰 `app/` 아래 라우트 파일 위치를 고른다(기존 구조 · 레이아웃 가드를 따른다 — 예: 마이 세부는 `app/my/`).
   경로 · 파일 이름을 요약에 적는다.
2. **조립은 공용 부품으로.** `src/components/ds/` 의 컴포넌트와 `src/design/ds/` 토큰으로 만든다. 새 색 · 크기가 필요하면
   `src/design/ds/` 에 **이름을 먼저 만든다**. 화면 로직이 커지면 `src/features/<도메인>/` 의 model · data · ui 경계를 따른다(`CLAUDE.md` 「BE 는 마지막에」).
3. **데이터.** 기존 API 로 되면 기존 `data/` 어댑터를 쓴다. 서버에 아직 없는 데이터면 — 앱 쪽은 `data/` 어댑터를 새로 두되
   **Lab 가짜 서버(`expo-lab/src/fake-server/`)에 임시 응답을 더해** 화면이 Lab 에서 보이게 하고, PR 「백엔드·스펙 영향」에
   **필요한 API(경로 · 요청 · 응답 모양)** 를 표로 남긴다. 실제 서버 주소 · 계약(`docs/api/openapi.json`)은 고치지 않는다.
4. **목록에 올린다.** `npm run lab:routes` 로 라우트 목록을 다시 만들고 `expo-lab/src/shell/routeMeta.ts` 에 한국어 제목 · 묶음을 단다
   (안 달면 동기화 테스트가 실패한다). 바로 열면 다른 화면으로 넘기는 가드가 있으면 `openVia` · `hint` 를 둔다.
5. **문서.** 화면 ID ↔ 라우트 매핑(`docs/PRODUCT.md` 표)과 `CLAUDE.md` 「지금 어디까지 왔나」 라우트 목록에 한 줄을 더한다.
   스펙(`docs/spec/**`)은 동결이라 쓰지 않는다 — 새 화면의 규칙 · 문안은 `docs/DESIGN.md` 에 적는다.
6. **테스트.** 화면 렌더 테스트 하나 이상(빈 데이터 · 보통 데이터), 새 어댑터면 형태 검증 테스트. 계측이 필요해 보이면 이벤트를
   만들지 말고 PR 「미결」에 제안만 적는다(`docs/ANALYTICS.md` 사전은 사람이 정한다).

## 함께 돌리는 검수 스킬

반영이 끝나고 검사(절차 6) 전에, 바뀐 범위에 맞는 저장소 검수 스킬을 **바뀐 화면 · 바뀐 문구에만** 돌린다(전체 앱 감사는 하지 않는다).

| 바뀐 것                                    | 스킬                     | 왜                                                                                                       |
| ------------------------------------------ | ------------------------ | -------------------------------------------------------------------------------------------------------- |
| 새 화면 · 화면 안 문구(버튼 · 안내 · 오류) | `momentory-ux-writing`   | 새 화면은 반드시 새 문구를 만든다 — 모멘토리 톤 · 「오류는 한 줄」 · 압박 금지를 사람이 보기 전에 맞춘다 |
| 색 · 글자 · 간격 · 새 화면 배치            | `momentory-design-audit` | 대비 · 터치 영역 · 토큰 사용 · 작은 화면 넘침을 값 단위로 확인한다                                       |

스킬이 찾은 것 중 **이번 요청 범위 안**은 고치고, 범위 밖은 고치지 말고 PR 「미결」에 적는다.

## 이미지 넣기

지시 · 새 화면에 붙은 이미지는 용도가 둘이다 — 프롬프트의 `[첨부] <경로> · 용도: … · 설명: …` 줄로 넘어온다.

- **참고용** — 보고 따라 만든다. **앱 파일로 넣지 않는다.**
- **앱에 넣기** — 그 그림을 앱에서 쓴다. 이렇게 넣는다:
  1. 자리: `assets/<영역>/`(예: `assets/rest/`, `assets/home/`) — 기존 폴더 관례를 따른다. 파일 이름은 영문 kebab-case.
  2. 손질: 사진 · 일러스트는 **WebP** 로(투명이 필요하면 알파 포함), 표시 크기의 3배 폭을 넘지 않게 줄인다. 배경을 빼야 하면
     `scripts/keyout-*.py` 와 같은 방식의 일회성 스크립트를 쓰거나 기존 것을 고친다(빌드에 끼우지 않는다 — `CLAUDE.md` 명령 절).
  3. 출처: 그 폴더 `README.md` 에 한 줄 — 파일 · 출처(사용자 제공 · 날짜 · 원본 이름) · 손질 내용. README 가 없으면 만든다.
  4. 쓰기: `expo-image`/`Image` 로 `require` 한다. 장식이면 낭독기에서 숨긴다(기존 장식 이미지 컴포넌트 관례 — 예 `features/home/ui/v2/Baba.tsx`). 의미가 있으면 짧은 대체 텍스트.
  5. Lab 에서 바꿔 끼울 수 있게 `src/design/studioAssets.ts` 에 등록할지 판단한다(화면별 값으로 고를 만한 그림이면 등록).
- **이미지를 새로 만들지 않는다** — Lab 실행 중에는 이미지 생성 도구(학교 게이트웨이 `ask.py image` 등)를 쓰지 않는다. 비용이 들고 실행마다
  사용자 승인이 필요하다(전역 규칙). 그림이 모자라면 보고에 「필요한 그림: 무엇 · 크기 · 들어갈 곳」으로 적는다.

## 하지 않는 것

- 넘긴 파일에 없는 디자인 변경을 「하는 김에」 끼워 넣지 않는다.
- `docs/spec/**` 은 동결 스냅샷이라 고치지 않는다. 스펙과 어긋나야 하면 `docs/PRODUCT.md` 「상류와 차이」에 기록한다.
- 실제 사용자 데이터 · 일기 내용은 넘기는 파일에 없다(가짜 서버 데이터뿐) — 있으면 외부로 보내지 않는다.
