# Lab 에서 AI 에게 맡기는 화면 작업 — 화면 고치기 · 새 화면 만들기

> **정본.** Expo Lab 「AI에게 맡기기」로 화면을 고치거나 새 화면을 만들 때 AI 가 따르는 규칙은 이 문서 하나다(2026-11-02 사용자 결정).
> 스킬 `momentory-lab-handoff`(`.claude/skills/` · `.agents/skills/`)는 이 문서를 따라 움직이는 손잡이일 뿐이다.
>
> **2026-11-02 개정** — Lab 안의 디자인 편집 · 시안 · 참고 시안 겹치기 · 「AI에게 넘기기」 파일(`momentory-handoff-*.json`)과
> 그 반영 스크립트(`design:apply*`)는 지웠다. 디자인을 바꾸는 일도 이제 **지시 + 참고 그림 첨부**로 맡긴다.

## 나누는 일

| 누가                         | 무엇을                                                                                                                                                                                                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **사람** (Lab)               | 화면을 고르고 화면 상태(기록 보통 · 기록 많음 · 불러오는 중 …) · 기기 · 글씨 크기로 살펴본 뒤, 「AI에게 맡기기」에 **무엇을 어떻게** 바꿀지 적는다. 원하는 모습의 그림(피그마 · 캡처)은 「참고용」, 앱에 넣을 그림은 「앱에 넣기」로 붙인다. 결과는 「수정 결과 보기」(A/B 의 B)로 본다. |
| **AI** (Claude Code · Codex) | 지시와 첨부를 근거로 코드를 고치고 · 검사를 돌리고 · 결과를 요약한다. 커밋 · PR 은 사람이 Lab 버튼으로 누른다. **머지는 사람이 결과를 보고 승인한 뒤에만.**                                                                                                                              |

## AI 의 절차

1. **읽고 요약해 확인받는다.** 지시 · 화면(라우트 · 파일) · 첨부(참고용 / 앱에 넣기)를 짧게 정리하고, 바꿀 값과 바꿀 구조를 나눠 적는다.
   값으로 안 되는 요청(배치 · 구조 · 새 요소)은 따로 묶어 「코드 작업이 필요한 것」으로 알린다. 범위가 크면 이 단계에서 진행 여부를 묻는다.
2. **브랜치.** main 이면 `design/<짧은 이름>` 같은 브랜치를 먼저 만든다(`docs/CONTRIBUTING.md`).
3. **고친다 — 값은 정의된 자리에서, 구조는 화면 코드에서.**
   - 공통 값(색 · 글자 · 간격)은 `src/design/ds/*.ts`, 화면별 값은 `src/design/studioApproved.json`, 탭 배경은 `src/design/tabBackgrounds.ts` 의
     `tabBackgroundByTab`(값은 같은 파일 `tabBackgroundAssets` 에 **이미 있는 배경 id** 만)이다. 계산되는 값(예: `withAlpha(primary.normal, …)`)이면
     원래 토큰이나 계산식을 고친다. 바꾼 이유와 전 → 후를 요약 · 커밋 메시지에 적는다.
   - 구조 차이는 참고 그림과 지시를 근거로 화면 코드를 고친다. 이때도 저장소 규칙이 이긴다:
     `docs/DESIGN.md` 우선(N0·N6) · 색은 `src/design/ds/` 에 **이름을 먼저 만들고** 쓴다(hex 하드코딩 금지) · 선택 상태를 색만으로 표시하지 않는다 ·
     오류는 한 줄로 · 숫자로 압박하지 않는다 · 폰트는 파일 이름으로 (`CLAUDE.md` 「자주 어기게 되는 것」). 지시나 그림이 이 규칙과 부딪히면 **고치지 말고** 부딪히는 점을 말한다.
4. **디자인 정본을 함께 고친다.** 토큰 값 · 규칙이 바뀌면 `docs/DESIGN.md` 의 해당 값도 고친다(정본이 둘로 갈라지지 않게).
   대비 보정 자리(`PLAN.md` A-5 · `ds/color.ts` 머리말)를 건드리면 그 표도 갱신한다.
5. **검사.** `npm run typecheck` · `npm run lint` · `npm run format:check` · `npm run test`(대비 테스트 `src/design/ds/__tests__/contrast.test.ts` 포함).
   대비 테스트가 깨지면 값을 억지로 바꾸지 말고 사용자에게 「이 색은 글자 대비(WCAG AA)를 못 넘는다 — 후보 둘」로 되묻는다.
6. **Lab 에서 다시 본다 — `momentory-lab-verify` 로 바뀐 화면을 전 · 후 비교한다(기기 · 화면 상태 · 글씨 크기).**
   스크립트 `expo-lab/scripts/lab-verify.mjs` 가 main 을 띄운 Lab(전)과 고친 코드를 띄운 Lab(후)에서 바뀐 라우트를 같은 조건으로 찍고,
   화소 차이와 배치 문제(가로 넘침 · 글자 잘림 · 탭바/안전 영역 가림 · 콘솔 오류 · 실패한 요청)를 `report.html` · `report.json` 으로 낸다.
   AI 는 보고서와 **그림을 직접 보고** 의도한 변경 · 의도하지 않은 변경 · 새로 생긴 문제를 나눠 보고한다. 사용자의 8085 Lab 은 읽기만 한다.
   참고 그림이 있으면 바뀐 화면과 나란히 놓고 눈으로 견준다.
7. **PR.** `.github/PULL_REQUEST_TEMPLATE.md` 형식. 「주요 변경」에 값 전 → 후 표, 「확인 방법」에 Lab 주소(라우트 · 기기 · 화면 상태), 「스크린샷」에 전 · 후 —
   절차 6 이 만든 `pr-screenshots.md` 조각을 쓴다(그림은 로컬 경로라 PR 편집창에 끌어 넣어 올린다 · 저장소에 커밋하지 않는다).
   **머지하지 않는다** — 사용자가 확인하고 승인한 뒤에만.

## Lab 에서 바로 맡길 때 (「AI에게 맡기기」 · 작업 공간)

Lab 패널에서 지시하면 서버가 **그 화면용 작업 공간**(저장소 바깥 git worktree + `lab/…` 브랜치 + 미리보기 Lab)을
첫 지시 때 만들고, 그 폴더에서 AI 를 돌린다. 지시 앞의 「AI에게 함께 보내는 정보」(`[화면]` · `[파일]` · `[환경]` — 그 뒤 `지시: ` 줄이 사용자가 적은 말)가 지금 보던 화면 · 기기 · 데이터를 알려 주고,
첨부 그림은 프롬프트의 `[첨부] <경로> · 용도: … · 설명: …` 줄로 넘어온다. 이때는 위 절차를 이렇게 바꾼다.

- 1(확인받기)은 **질문하지 않고 요약을 출력으로 남기는 것**으로 대신한다. 규칙과 부딪히거나 값으로 안 되는 큰 구조 변경은 하지 말고 보고만 한다.
- 2(브랜치)는 이미 있다 — 새로 만들지 않는다.
- 6(Lab 확인)은 생략 — 사용자가 미리보기(A/B 의 B · 같은 화면 상태로 뜬다)에서 본다. 전 · 후 비교 보고서가 필요하면 **Lab 실행기가 AI 가 끝난 뒤**
  `node expo-lab/scripts/lab-verify.mjs --before <main Lab> --after <미리보기 주소> --changed --repo <작업 공간>` 을 돌려 붙일 수 있다(실행기 몫 — AI 가 부르지 않는다).
- 7 대신 **커밋 · push · PR 을 하지 않는다.** 끝에 `COMMIT_MESSAGE:` 블록(한국어 `type: 문장형` + 본문 · Co-Authored-By 없음)과
  `PR_BODY:` 블록(`.github/PULL_REQUEST_TEMPLATE.md` 형식)을 출력한다. 사용자가 Lab 의 「수정 저장(커밋)」 · 「검토 요청 올리기(PR)」를 누른다.

### 시안 여러 개 (「시안 개수」 2 · 3)

같은 지시로 시안을 여럿 만들 때는 시안마다 작업 공간이 따로이고, Lab 이 **동시에** 돌린다. 서로의 결과를 볼 수 없어서 방향을 미리 나눠 준다. 프롬프트에 이렇게 붙는다.

```
[시안 2 / 3]
- 같은 지시로 시안 3개를 따로 만든다 — 이 작업 공간은 그중 시안 2 다. …
- 이 시안이 맡은 방향: 구성을 과감하게 — …
- 시안 1 이 맡은 방향(이쪽과 겹치지 않게): 지시를 가장 곧게 따르는 정석 — …
- 시안 3 이 맡은 방향(이쪽과 겹치지 않게): 덜어 내는 방향 — …
```

- **맡은 방향을 끝까지** — 다른 시안이 맡은 방향과 겹치지 않게 밀고 간다. 지시와 부딪히면 지시가 먼저다.
- **저장소 규칙은 그대로다** — 다르게 만들려고 규칙(`docs/DESIGN.md` · 대비 · 「오류는 한 줄」 · 숫자 압박 금지)을 어기지 않는다.
- **다른 시안의 폴더를 열지 않는다** — 다른 시안은 프롬프트의 방향 줄로만 안다.
- **시안은 초안이다** — 바뀐 파일만 검사한다(`npx prettier --check <파일>` · `npx eslint <파일>` · `npx jest <경로> --maxWorkers=2`). 저장소 전체 검사(`typecheck` · `lint` · `format:check`)는 돌리지 않는다. 고른 시안을 저장할 때 Lab 의 저장 전 검사가 전체를 본다.
- **summary 첫 줄은 「방향: …」 한 줄** — Lab 이 시안 비교 화면의 폰 머리에 그 줄을 띄운다.
- 나머지(고치고 검사까지만 · 커밋 · push · PR 하지 않기 · 끝 블록)는 위 「Lab 에서 바로 맡길 때」 그대로다. 사용자가 시안을 나란히 보고 하나를 골라 Lab 에서 확정(저장 + 검토 요청)하고, 나머지 시안은 버린다.

## 새 화면 만들기

Lab 의 「＋ 새 화면 만들기」로 맡기면 넘어오는 것: 화면 이름 · 들어갈 곳(묶음) · 어떤 화면인지 설명 · (선택) 참고 그림.
위 절차에 더해 —

1. **자리를 정한다.** 들어갈 묶음에 맞춰 `app/` 아래 라우트 파일 위치를 고른다(기존 구조 · 레이아웃 가드를 따른다 — 예: 마이 세부는 `app/my/`).
   경로 · 파일 이름을 요약에 적는다.
2. **조립은 공용 부품으로.** `src/components/ds/` 의 컴포넌트와 `src/design/ds/` 토큰으로 만든다. 새 색 · 크기가 필요하면
   `src/design/ds/` 에 **이름을 먼저 만든다**. 화면 로직이 커지면 `src/features/<도메인>/` 의 model · data · ui 경계를 따른다(`CLAUDE.md` 「BE 는 마지막에」).
3. **데이터.** 기존 API 로 되면 기존 `data/` 어댑터를 쓴다. 서버에 아직 없는 데이터면 — 앱 쪽은 `data/` 어댑터를 새로 두되
   **Lab 가짜 서버(`expo-lab/src/fake-server/`)에 임시 응답을 더해** 화면이 Lab 에서 보이게 하고, PR 「백엔드·스펙 영향」에
   **필요한 API(경로 · 요청 · 응답 모양)** 를 표로 남긴다. 실제 서버 주소 · 계약(`docs/api/openapi.json`)은 고치지 않는다.
4. **목록에 올린다.** `npm run lab:routes` 로 라우트 목록을 다시 만들고 `expo-lab/src/shell/routeMeta.ts` 에 한국어 제목 · 묶음을 단다
   (안 달면 동기화 테스트가 실패한다). 바로 열면 다른 화면으로 넘기는 가드가 있으면 `openVia` · `hint` 를 둔다.
5. **문서.** 화면 ID ↔ 라우트 매핑(`docs/PRODUCT.md` 표)과 `CLAUDE.md` 「지금 어디까지 왔나」 라우트 목록에 한 줄을 더한다.
   스펙(`docs/spec/**`)은 동결이라 쓰지 않는다 — 새 화면의 규칙 · 문안은 `docs/DESIGN.md` 에 적는다.
6. **테스트.** 화면 렌더 테스트 하나 이상(빈 데이터 · 보통 데이터), 새 어댑터면 형태 검증 테스트. 계측이 필요해 보이면 이벤트를
   만들지 말고 PR 「미결」에 제안만 적는다(`docs/ANALYTICS.md` 사전은 사람이 정한다).

## 함께 돌리는 검수 스킬

고친 뒤 검사(절차 5) 전에, 바뀐 범위에 맞는 저장소 검수 스킬을 **바뀐 화면 · 바뀐 문구에만** 돌린다(전체 앱 감사는 하지 않는다).

| 바뀐 것                                    | 스킬                     | 왜                                                                                                       |
| ------------------------------------------ | ------------------------ | -------------------------------------------------------------------------------------------------------- |
| 새 화면 · 화면 안 문구(버튼 · 안내 · 오류) | `momentory-ux-writing`   | 새 화면은 반드시 새 문구를 만든다 — 모멘토리 톤 · 「오류는 한 줄」 · 압박 금지를 사람이 보기 전에 맞춘다 |
| 색 · 글자 · 간격 · 새 화면 배치            | `momentory-design-audit` | 대비 · 터치 영역 · 토큰 사용 · 작은 화면 넘침을 값 단위로 확인한다                                       |

스킬이 찾은 것 중 **이번 요청 범위 안**은 고치고, 범위 밖은 고치지 말고 PR 「미결」에 적는다.

## 이미지 넣기

지시 · 새 화면에 붙은 이미지는 용도가 둘이다 — 프롬프트의 `[첨부] <경로> · 용도: … · 설명: …` 줄로 넘어온다.

- **참고용** — 보고 따라 만든다(피그마 · Claude Design 시안 캡처 등). **앱 파일로 넣지 않는다.**
- **앱에 넣기** — 그 그림을 앱에서 쓴다. 이렇게 넣는다:
  1. 자리: `assets/<영역>/`(예: `assets/rest/`, `assets/home/`) — 기존 폴더 관례를 따른다. 파일 이름은 영문 kebab-case.
  2. 손질: 사진 · 일러스트는 **WebP** 로(투명이 필요하면 알파 포함), 표시 크기의 3배 폭을 넘지 않게 줄인다. 배경을 빼야 하면
     `scripts/keyout-*.py` 와 같은 방식의 일회성 스크립트를 쓰거나 기존 것을 고친다(빌드에 끼우지 않는다 — `CLAUDE.md` 명령 절).
  3. 출처: 그 폴더 `README.md` 에 한 줄 — 파일 · 출처(사용자 제공 · 날짜 · 원본 이름) · 손질 내용. README 가 없으면 만든다.
  4. 쓰기: `expo-image`/`Image` 로 `require` 한다. 장식이면 낭독기에서 숨긴다(기존 장식 이미지 컴포넌트 관례 — 예 `features/home/ui/v2/Baba.tsx`). 의미가 있으면 짧은 대체 텍스트.
  5. 화면별 값(`src/design/studioApproved.json`)이 id 로 그림을 고르는 자리(예: 쉼터 `rest.babaImage.assetId`)면 `src/design/studioAssets.ts` 에 등록하고 id 로 고른다.
- **이미지를 새로 만들지 않는다** — Lab 실행 중에는 이미지 생성 도구(학교 게이트웨이 `ask.py image` 등)를 쓰지 않는다. 비용이 들고 실행마다
  사용자 승인이 필요하다(전역 규칙). 그림이 모자라면 보고에 「필요한 그림: 무엇 · 크기 · 들어갈 곳」으로 적는다.

## 하지 않는 것

- 지시 · 첨부에 없는 디자인 변경을 「하는 김에」 끼워 넣지 않는다.
- `docs/spec/**` 은 동결 스냅샷이라 고치지 않는다. 스펙과 어긋나야 하면 `docs/PRODUCT.md` 「상류와 차이」에 기록한다.
- 실제 사용자 데이터 · 일기 내용은 첨부에 없다(Lab 은 가짜 서버 데이터뿐) — 있으면 외부로 보내지 않는다.
