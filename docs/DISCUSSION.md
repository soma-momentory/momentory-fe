## §1. BE 팀과 — API 계약

엔티티 7종(`momentory.schema.mvp.json`)의 CRUD 는 스키마가 이미 말하고,
**엔드포인트의 모양은 [`api/openapi.json`](api/openapi.json) 이 말한다**(2026-08-10 반입).
합의가 필요한 것은 **둘 다 말하지 않는 것들**이다.

### 1-1. 멱등성 규약 — FE 가 제안하는 안 (`ARCHITECTURE.md` §7)

앱은 local-first 다 — 기기에 먼저 저장하고 아웃박스 큐로 올린다. 비행기
모드에서 쓴 일기가 재연결 때 **두 번 만들어지지 않으려면** 아래가 계약에
들어가야 한다. FE 안이 이미 있으므로 **BE 의 수용 여부**가 질문이다:

- **ID 는 클라이언트가 만든다** (ULID). 같은 `id` 생성 요청이 두 번 오면
  두 번째는 기존 리소스를 200 으로 돌려준다 — 서버 채번 없음
- **mutation 마다 `Idempotency-Key`** — 재시도에도 키를 바꾸지 않고, 서버는
  키별 결과를 **최소 24시간** 보관해 같은 응답을 재생한다
- **갱신은 `If-Match`(버전) 선행조건** — 어긋나면 409. 특히 `A4` 일기 수정은
  원문을 보관하지 않으므로 덮어쓰면 복구가 불가능하다
- `Moment.syncState: local | uploading | synced` — **"실패" 상태가 없다.**
  실패로 표시하지 않고 「올리는 중」이 스키마 규칙이다. 서버 에러 코드가
  이 3상태로 접히는 방식을 합의한다

### 1-2. 회고 대화 — 방향별 응답 생성 (⛔ 최우선)

지금 `FOLLOW_UPS`(`retro.ts`) 는 `reframe` 데모 한 갈래뿐이라 **어떤 방향을
골라도 같은 대사가 나온다.** 나머지 세 방향의 대사를 지어내지 않았다 —
서버가 방향(`Retro.direction`)과 그때까지의 대화를 받아 생성하는 것이 전제다.

- 대화 API 의 형태 — 요청/응답 단위인가, **스트리밍**인가? (스트리밍이면
  `TYPING_MS` 타이핑 연출 자리를 대체한다)
- 바바의 발화 페르소나·안전 규칙(위기 감지 `E13` 연동 포함)을 누가 어디서
  거는가 — 프롬프트가 서버 소관이면 FE 는 문안을 갖지 않는다
- 회고 중단·재개(`Retro.step`) 시 대화 이력 복원 계약

### 1-3. 일기·리포트 생성 — 서버가 쓰는 문장의 범위

- **`C6` 일기 초안** — 본문 · 바바의 관점 · 관점의 근거 · 행동의 「상황」 ·
  이야기 속 감정. 지금은 `DRAFT_DEMO` 하나다. 전부 대화 전체를 읽어야
  나오는 값 — 생성 시점(회고 종료 즉시? 비동기?)과 실패 시 폴백을 정한다
- **`W1` 주간 해석** — 지금 `SAMPLE_REPORT_ANALYSIS` 표가 주차별 문장
  5종(요약 · 흐름 라벨 · 흐름 비교 · 감정 흐름 · 이어갈 한 가지)을 데모로
  갖고 있다. **수치는 전부 FE 계산**(회고 수 · 감정 수 · 이전 주 N회 · 행동
  만든/해본 수)이다 — 서버가 붙어도 이 분담을 유지할지, 수치도 서버가
  내려줄지 합의한다. **주차 이동 범위(어느 주까지 넘겨볼 수 있나)는 서버가
  정한다**는 것이 FE 전제다
- 리포트 잠금 — 일기 7편 기준(`REPORT_UNLOCK_COUNT`)을 서버도 같은 수로
  판정하는지 (FE 만 세면 기기 간 어긋난다)

### 1-4. 캘린더 일정 동기화

`source: external` 일정은 **읽기 전용 + `hidden`**(삭제 대신 숨김)이 규칙이다.
`externalId` 매칭 · 기기 캘린더와 서버의 동기화 방향(기기→서버 단방향이면
충분한가) · 숨김의 저장 위치를 정한다.

### 1-5. 서버 보관·삭제 — §2 와 겹치는 질문

- 서버측 저장 암호화(at rest) 수준 — **화면에 약속으로 쓰지 않더라도**
  (`RULES.md` — 확정 아닌 약속 금지) 내부 계약으로는 필요하다
- **회원 탈퇴 시 서버가 실제로 무엇을 언제까지 지우는가** — 즉시 삭제인가,
  유예(soft delete) 기간이 있는가. FE 는 이 답이 있어야 탈퇴 확인 화면
  (`my.pendingStates`, 아직 없음)의 문안을 쓸 수 있다

### 1-6. 인증 — 카카오 로그인·갱신·로그아웃은 붙었고 **HTTPS 가 비어 있다** (2026-08-07 추가 · 2026-08-09 갱신 닫힘 · 2026-08-10 로그아웃 닫힘)

`POST /api/v1/auth/kakao` 는 합의돼 구현했다(요청 `{accessToken}` → 응답
`accessToken`·`refreshToken`·`tokenType`·`accessTokenExpiresIn`·`userId`·`onboardingRequired`,
오류 `400 INVALID_REQUEST` · `401 KAKAO_TOKEN_INVALID` · `502 KAKAO_API_SERVER_ERROR` ·
`503 KAKAO_API_NETWORK_ERROR`).

✅ **갱신(refresh)도 닫혔다** — BE 가 이미 `POST /api/v1/auth/reissue` 를 구현해
두었다(요청 `{refreshToken}` → 응답 `accessToken`·`refreshToken`·`tokenType`·
`accessTokenExpiresIn`, 오류 `400 INVALID_REQUEST` · `401 REFRESH_TOKEN_INVALID` /
`REFRESH_TOKEN_REVOKED` / `REFRESH_TOKEN_EXPIRED`). refresh token 은 **회전한다**
(한 번 쓰면 폐기하고 새것을 준다). FE 는 `reissueApi.ts` + `auth.ts` 의
`getAccessToken`/`hydrate` 에서 붙였다 — `TASKS.md` 「2026-08-09 · 토큰 갱신」.

✅ **로그아웃도 닫혔다** — `POST /api/v1/auth/logout`(요청 `{refreshToken}` →
**`204` 본문 없음**, 오류 `400 INVALID_REQUEST`). **제출한 refresh token 하나만
멱등적으로 폐기한다** — 다른 기기의 세션은 살아 있고, 같은 토큰을 두 번 보내도
결과가 같다. FE 는 `logoutApi.ts` + `auth.ts` 의 `signOut` 에서 붙였고,
**로컬을 먼저 비우고 폐기는 기다리지 않는다**(서버가 죽어 있어도 로그아웃은 끝난다).

**남은 하나가 운영 배포를 막는다:**

- ⛔ **개발 서버가 평문 HTTP(IP 주소)다.** Android 는 그 호스트 하나만 예외로 열었지만
  (`plugins/withInsecureDevApi.ts`) **iOS 는 ATS 가 IP 예외를 지원하지 않아 앱 전체
  예외 말고는 좁힐 방법이 없다.** 스토어 빌드에는 쓸 수 없다 — 서버에 HTTPS(가능하면
  IP 가 아닌 도메인까지)가 필요하다. 준비되면 FE 는 `.env` 한 줄만 바꾼다.
- 그 밖에 정해야 할 것: **회원 탈퇴 시** 서버측 토큰 폐기(로그아웃과 달리 그 계정의
  **모든 기기** 세션을 끊어야 하고, 삭제 범위·유예는 §1-5 가 열려 있다) · 401 을 받았을 때
  아웃박스(§1-1)와 세션의 관계 · Apple·Google 세션 교환 엔드포인트(카카오와 같은 형태인가).

### 1-8. 보관함·리포트·마이가 볼 엔드포인트가 없다 (⛔ **화면 10장을 막는다** · 2026-08-11 추가)

**계약 18개를 다 붙였는데 화면 10장이 여전히 `src/mocks/sample.ts` 를 본다.**
연결할 것이 남아서가 아니라 **계약에 없어서**다. 지금 §1 에서 유일하게 코드로
막혀 있는 안건이고, 리드타임이 있으니 가장 먼저 말해야 한다.

| 화면                    | 무엇이 필요한가           | 지금 계약                                                        |
| ----------------------- | ------------------------- | ---------------------------------------------------------------- |
| `A1` `A2` 보관함        | **일기 목록**(달·기간별)  | 없다                                                             |
| `A3` `A3-b` `A3-c` 일기 | 일기 하나 + 행동 카드     | `GET /retrospect/{id}/diary` — **회고 id 를 이미 알아야 열린다** |
| `A4` 일기 수정          | 내 문장·감정 태그 수정    | 없다                                                             |
| `A3-c` 행동 카드 완료   | 카드 완료 토글            | 없다                                                             |
| `W1` 리포트             | 주간 집계 + 해석 문장 5종 | 없다 (문장의 **범위**는 §1-3)                                    |
| `M1` 마이               | 전체 기간 통계            | 없다                                                             |

**우리 쪽 모양은 이미 정해져 있다** — `momentory.schema.mvp.json` 의 `Diary` ·
`ActionCard` 이고 FE 타입이 그대로 든다(`src/features/diary/model/types.ts`).
`Diary` 는 `body` · `babaView` · `babaViewBasis` · `emotions` · `authoredBy` ·
`editedAt` · `ordinal` · `retrospectId` · `storyEmotion` · `startEmotion` ·
`weather` 를, `ActionCard` 는 `situation` · `targetAction` · `done` · `doneAt` 을 갖는다.
회고가 끝나면 서버가 이미 이것들을 만들고 있다 — **만들어 둔 것을 다시 꺼낼 길이
없는 것**이 문제다.

정해야 할 것:

1. **목록의 단위와 범위** — 달 단위(`?month=YYYY-MM`)인가 기간(`?from=&to=`)인가.
   `A1` 은 달력이라 달로 열고, `A2` 목록도 같은 달을 본다. **어느 달까지 넘겨볼 수
   있는지는 서버가 정한다**는 것이 FE 전제다(리포트의 주차 이동과 같은 규칙 — §1-3)
2. **행동 카드를 일기에 실어 줄 것인가, 따로 줄 것인가** — 화면은 언제나 같이
   쓴다(`A3` 두 면 · `C6-b`). 따로면 목록에서 카드 유무를 알 수 없어 한 번 더 부른다
3. **일기 수정의 범위** — `A4` 는 **내 문장과 감정 태그만** 고친다(바바의 관점은
   못 고친다). `PATCH` 로 그 둘만 받으면 되고, `editedAt` 은 서버가 찍는가
4. **파생값을 누가 세는가** — 지금은 FE 가 전부 센다(`features/{archive,report,my}/model/`).
   리포트 잠금(일기 7편 · `REPORT_UNLOCK_COUNT`)도 FE 판정이라 **기기 간 어긋난다.**
   §1-3 과 [`PRODUCT.md` 「상류와 차이」](PRODUCT.md) 3번이 같은 질문을 열어 뒀다 —
   목록 엔드포인트가 생기는 김에 함께 정한다

**세지 않는 것은 그대로다** — 연속 일수·점수·배지는 스키마가 금지한다(`RULES.md`).
서버가 내려줘도 화면은 그리지 않는다.

## §2. 팀 전체 — `DATA-SECURITY.md` 를 세우기 위한 결정

문서 대부분(기기 내 저장 배치 · MMKV 암호화 키를 SecureStore 에 두는 구조 ·

**못 정하는 것이 셋**이고, 이것만 팀 결정이다:

> 문서가 생겼다고 화면에 약속이 되살아나면 안 된다.
