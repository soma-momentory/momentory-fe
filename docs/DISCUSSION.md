## §1. BE 팀과 — API 계약

엔티티 7종(`momentory.schema.mvp.json`)의 CRUD 는 스키마가 이미 말하고,
**엔드포인트의 모양은 [`api/openapi.json`](api/openapi.json) 이 말한다**(2026-08-10 반입).

### 1-1. 멱등성 규약 — FE 가 제안하는 안 (`ARCHITECTURE.md` §7)

> ⛔ **2026-08-21 — 아직 아무것도 없다.** BE 코드 전체에 `Idempotency-Key`·`If-Match`·
> `ETag` 를 읽는 자리가 **하나도 없고**, id 는 전부 서버가 채번한다(`Long` · JPA
> `@GeneratedValue`). 스키마가 정한 ULID 클라이언트 생성과도 어긋난다.
> **§1 에서 유일하게 코드로 막고 있는 안건**이고, M3-3 아웃박스가 여기 걸려 있다.
>
> 지금은 드러나지 않는다 — 붙어 있는 쓰기가 전부 **화면이 기다리는 동기 호출**이라
> 재시도를 큐가 아니라 사용자가 한다. 아웃박스가 생기는 순간 실제 문제가 된다.

앱은 local-first 다 — 기기에 먼저 저장하고 아웃박스 큐로 올린다. 비행기
모드에서 쓴 일기가 재연결 때 **두 번 만들어지지 않으려면** 아래가 계약에
들어가야 한다. FE 안이 이미 있으므로 **BE 의 수용 여부**가 질문이다:

- **ID 는 클라이언트가 만든다** (ULID). 같은 `id` 생성 요청이 두 번 오면
  두 번째는 기존 리소스를 200 으로 돌려준다 — 서버 채번 없음
- **mutation 마다 `Idempotency-Key`** — 재시도에도 키를 바꾸지 않고, 서버는
  키별 결과를 **최소 24시간** 보관해 같은 응답을 재생한다
- **갱신은 `If-Match`(버전) 선행조건** — 어긋나면 409. 특히 `A4` 일기 수정은
  원문을 보관하지 않으므로 덮어쓰면 복구가 불가능하다
- `Moment.syncState: local | uploading | synced` — **"실패" 상태가 없다.**
  실패로 표시하지 않고 「올리는 중」이 스키마 규칙이다. 서버 에러 코드가
  이 3상태로 접히는 방식을 합의한다

### 1-4. 캘린더 일정 동기화 — ✅ **닫혔다** (2026-08-21 · BE `40da034` 대조)

> ✅ **BE 가 전부 냈고 FE 가 붙였다.** 아래 절은 **어떻게 닫혔는지의 기록**이다 —
> 열린 질문은 3번 하나(연동을 껐을 때)뿐이고, 그건 BE 이전에 제품 결정이다.
>
> | 물었던 것       | 지금 서버                                                                                           |
> | --------------- | --------------------------------------------------------------------------------------------------- |
> | 화해 엔드포인트 | ✅ `POST /api/v1/schedules/sync` — `{ from, to, events[] }` → `{ created, updated, deleted }`       |
> | `source`        | ✅ `ScheduleResponse.source` (`MANUAL` · `CALENDAR`)                                                |
> | `hidden`        | ✅ `ScheduleResponse.hidden` + `PATCH /api/v1/schedules/{id}/visibility`                            |
> | `externalId`    | △ **요청에만 있다.** `CalendarSyncEventRequest` 는 받지만 `ScheduleResponse` 는 **돌려주지 않는다** |
>
> ⚠ **결정문과 구현이 한 자리 다르다.** 아래 1번은 「`PATCH /schedules/{id}` 는 캘린더
> 일정에 **`hidden` 만** 허용」으로 적혀 있는데, BE 는 **별도 엔드포인트**
> `PATCH /schedules/{id}/visibility`(`204`)를 뒀다. `PATCH /schedules/{id}` 는
> **`source=MANUAL` 만** 찾으므로 캘린더 일정에 부르면 `404 SCHEDULE_NOT_FOUND` 다.
> `DELETE` 도 같다 — 「거부」가 아니라 **404** 로 온다(`ScheduleService`).
> FE `scheduleApi.ts` 는 이미 구현 쪽으로 붙어 있다.
>
> ⚠ **`externalId` 가 응답에 없어서 남는 것 하나** — 화면은 서버 일정이 어느 기기
> 이벤트에서 왔는지 모른다. 지금은 `source` 만으로 읽기 전용 판정이 되므로 문제가
> 없지만, 「이 일정을 캘린더 앱에서 열기」류가 생기면 그때 필요해진다.
>
> 서버가 실제로 하는 화해(BE `ScheduleService.syncCalendar` 확인): 대상은
> `user` AND `source=CALENDAR` AND `date ∈ [from, to]` 뿐 · `externalId` 로 upsert ·
> `date`·`title` 만 덮고 **`hidden`·`completed`·`emotion` 은 보존** · 범위 안에서
> 스냅샷에 없는 것은 **소프트 삭제**(`deleted_at`) · **같은 `externalId` 가 두 번 오면
> `400`**(`INVALID_REQUEST`) · `events: []` 는 정상.

`source: external` 일정은 **읽기 전용 + `hidden`**(삭제 대신 숨김)이 규칙이다.

**2026-08-11 — 제품이 방향을 정했다:**

- 캘린더는 **앱이 기기에서 직접 읽는다**(`expo-calendar`). 서버가 구글·애플
  캘린더를 대신 부르지 않는다
- 읽은 일정을 **서버에 넣는다.** 그 뒤로 화면은 서버에서 하루치를 받는다
  (`GET /api/v1/schedules?date=` — 이미 붙어 있다)
- **동기화는 사용자가 앱을 열 때마다** 새 일정이 있는지 훑어서 가져온다

**앞서 「캘린더가 붙을 때 문제가 된다」고 미뤄둔 셋은 이렇게 닫혔다** —
`ScheduleResponse` 에 둘이 들어왔고, 하나는 요청에만 들어왔다:

| 필드         | 이 설계에서 왜 필요했나                                                                                                                                         | 지금                                           |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `externalId` | **앱을 열 때마다 훑는다** — 기기 이벤트 키로 upsert 하지 않으면 같은 일정이 열 때마다 새로 만들어진다. §1-1 멱등성과 같은 문제다                                | △ **요청에만** — 서버가 이 키로 upsert 한다    |
| `source`     | 읽기 전용 판정 — `calendar` 는 제목 수정이 없고 삭제 대신 숨김이다(`12-c`). 지금은 구분이 없어 **홈이 "캘린더에서 가져왔어요"라고 말하면서 전부 수동 일정**이다 | ✅ `ScheduleResponse.source`                   |
| `hidden`     | 숨김이 서버에 없으면 **다음 동기화가 숨긴 일정을 되살린다.** 기기 메모리에만 있는 지금은 앱을 껐다 켜기만 해도 이미 풀린다                                      | ✅ `ScheduleResponse.hidden` · 화해가 보존한다 |

어댑터가 `source` 를 소문자로 옮기는 자리는 `src/features/home/data/scheduleApi.ts` 의 표다.

**✅ 정해진 것 — 기기에서 지운 일정은 서버에서도 지운다** (2026-08-11 제품 결정)

기기 캘린더가 정본이고 서버는 그 사본이다. 원본이 없어지면 사본도 없앤다.

> ⚠ **대가**: 그 일정에 남긴 **감정과 마침 기록이 함께 사라진다.** 캘린더에서
> 일정 하나를 지우는 것이 회고 재료(`C2` 가 읽는 「오늘 기록한 감정」)를 지우는
> 일이 된다 — 사용자는 두 행동을 같은 것으로 여기지 않을 수 있다. 알고 고른
> 것이므로 여기까지가 기록이다.

**이 답이 동기화의 모양을 바꾼다.** 「새 것이 있나 훑는다」로는 **지워진 것을 알
수 없다** — 없는 것은 훑어도 나오지 않는다. 지운 것을 알려면 **훑은 범위의 기기
일정 전부와 서버의 그 범위를 맞춰봐야 한다.** 즉 동기화는 추가가 아니라
**화해(reconcile)**다:

```
POST /api/v1/schedules/sync
  { from, to, events: [{ externalId, date, title }, …] }   ← 그 범위의 기기 일정 전부
서버: externalId 로 upsert · 그 범위에서 목록에 없는 calendar 일정은 삭제
```

**세 가지가 이 모양에 딸려 온다:**

- **삭제는 `source: calendar` 에만.** 수동 일정(`12-e`)은 기기 캘린더에 없으므로
  같은 규칙을 적용하면 **직접 추가한 일정이 앱을 열 때마다 사라진다**
- **삭제는 보낸 범위 안에서만.** 오늘 하루만 훑고 전체를 맞춰보면 과거가 날아간다
- **`hidden` 은 삭제와 다르다.** 숨긴 일정은 기기에 여전히 있으므로 다음 화해에도
  살아남아야 한다 — 서버가 `hidden` 을 들고 upsert 때 보존한다

### 1-6. 인증 — 로그인·갱신·로그아웃·**HTTPS 까지 닫혔다** (2026-08-07 추가 · 갱신 2026-08-09 · 로그아웃 2026-08-10 · **HTTPS 2026-08-25**)

`POST /api/v1/auth/kakao` 는 합의돼 구현했다(요청 `{accessToken}` → 응답
`accessToken`·`refreshToken`·`tokenType`·`accessTokenExpiresIn`·`userId`·`onboardingRequired`,
오류 `400 INVALID_REQUEST` · `401 KAKAO_TOKEN_INVALID` · `502 KAKAO_API_SERVER_ERROR` ·
`503 KAKAO_API_NETWORK_ERROR`).

✅ **갱신(refresh)도 닫혔다** — BE 가 이미 `POST /api/v1/auth/reissue` 를 구현해
두었다(요청 `{refreshToken}` → 응답 `accessToken`·`refreshToken`·`tokenType`·
`accessTokenExpiresIn`, 오류 `400 INVALID_REQUEST` · `401 REFRESH_TOKEN_INVALID` /
`REFRESH_TOKEN_REVOKED` / `REFRESH_TOKEN_EXPIRED`). refresh token 은 **회전한다**
(한 번 쓰면 폐기하고 새것을 준다). FE 는 `reissueApi.ts` + `auth.ts` 의
`getAccessToken`/`hydrate` 에서 붙였다 — `TASKS.md` 「2026-08-09 · 토큰 갱신」.

✅ **로그아웃도 닫혔다** — `POST /api/v1/auth/logout`(요청 `{refreshToken}` →
**`204` 본문 없음**, 오류 `400 INVALID_REQUEST`). **제출한 refresh token 하나만
멱등적으로 폐기한다** — 다른 기기의 세션은 살아 있고, 같은 토큰을 두 번 보내도
결과가 같다. FE 는 `logoutApi.ts` + `auth.ts` 의 `signOut` 에서 붙였고,
**로컬을 먼저 비우고 폐기는 기다리지 않는다**(서버가 죽어 있어도 로그아웃은 끝난다).

> **2026-08-21 · BE 코드에서 확인한 것** — access token 수명은 **30분**
> (`jwt.access-token-expiration: 30m`), refresh 수명은 배포 환경변수
> (`JWT_REFRESH_EXPIRATION`)라 저장소에서는 알 수 없다. 인증 없이 열린 경로는
> 넷뿐이고(`/actuator/health` · `/swagger-ui/**` · `/v3/api-docs/**` · `/api/v1/auth/**`),
> 세션은 stateless · CSRF 비활성이다.
>
> ⚠ **`/swagger-ui/**` 와 `/v3/api-docs/**` 가 운영에서도 기본 켜짐이다** —
> `application-prod.yml` 이 `${SWAGGER_ENABLED:true}` 라 환경변수를 안 주면 열린다.
> 그 둘이 `PUBLIC_PATHS` 라 토큰 없이 계약 전문이 보인다. **FE 를 막지는 않지만**
> (오히려 `sync:api` 가 이걸 쓴다) 배포 전에 BE 에 확인할 자리다.
>
> ⚠ **회원 탈퇴 엔드포인트는 아직 없다.** BE 전체에 사용자 삭제 경로가 없고,
> `POST /api/v1/auth/logout` 은 **제출한 refresh token 하나만** 폐기한다 —
> 「그 계정의 모든 기기 세션을 끊는다」는 지금 서버가 못 하는 일이다(§1-5 · `DATA-SECURITY.md` §4).

### 1-9. 「하루」의 경계가 서버와 다르다 (⚠ **2026-08-21 추가 · BE 코드 대조에서 나왔다**)

**서버의 하루는 KST 자정에 바뀌고, 앱의 하루는 04:00 에 바뀐다.**

| 어디   | 경계         | 근거                                                                                      |
| ------ | ------------ | ----------------------------------------------------------------------------------------- |
| 서버   | **KST 자정** | `TimeZonePolicy.DEFAULT_ZONE_ID = Asia/Seoul` · 월 조회와 「하루 한 번」 가드가 같이 쓴다 |
| 프론트 | **04:00**    | `src/lib/clock.ts` — "오전 0~3시는 아직 어제"                                             |

**실제로 갈리는 자리는 회고 「하루 한 번」 가드 하나다.** 서버는
`RetrospectService.requireNoDiaryToday` 가 **KST 자정** 기준으로 오늘 일기가 있으면
`409 ALREADY_RETROSPECTED_TODAY` 를 낸다. 화면은 앱-하루(04:00)로 센다. 그래서:

- 21일 23:00 에 회고를 마치고 **22일 01:00** 에 다시 열면 — 서버는 **허용**하고
  화면은 「오늘 이미 했다」로 막으려 한다
- 22일 02:00 에 회고를 마치고 **22일 10:00** 에 다시 열면 — 화면은 새 하루로 보고
  서버가 **409** 로 막는다

**지금 깨지지는 않는다** — `retroApi.ts` 가 그 409 를 안내 한 줄로 흡수하기 때문이다
(모달을 띄우지 않는다는 규칙과도 맞는다). 다만 **사용자가 보는 「오늘」이 둘**이라는
사실은 남는다.

월 조회는 어긋나지 않는다 — `diaryApi.ts` 의 `kstDate` 가 **일부러 서버 경계에
맞춰져 있다.** 즉 이미 한 저장소 안에 경계가 두 개 있고, 어느 쪽이 어디에 쓰이는지가
파일 주석에만 적혀 있다.

**정할 것 둘:**

1. **서버의 하루를 04:00 로 옮길 것인가**(`TimeZonePolicy` 옆에 「하루 경계」를 두면
   된다) — 옮기면 화면과 서버가 같은 「오늘」을 말한다. 월 조회 창도 함께 밀린다
2. **아니면 앱이 서버 경계를 따를 것인가** — `clock.ts` 의 04:00 은 「새벽에 쓰는
   회고는 어제의 회고」라는 제품 판단이라, 뒤집으면 그 판단이 사라진다

FE 는 **1번을 제안한다** — 04:00 은 제품 규칙이고 KST 자정은 구현 기본값이라,
근거의 무게가 다르다. 다만 서버가 이미 쌓은 데이터의 월 경계가 바뀌므로 BE 판단이다.

### 1-10. 애플 세션 교환 — ✅ **닫혔다** (2026-08-24 · 교환 + nonce · 남은 것은 탈퇴 revoke 하나)

**닫혔다.** BE 가 `POST /api/v1/auth/apple` 을 냈고(`AppleLoginController`),
FE 가 같은 날 붙였다(`src/features/auth/data/appleAuthApi.ts`).
계약은 [`api/openapi.json`](api/openapi.json) 에 반입돼 있다(엔드포인트 32개).

이 절을 지우지 않고 남겨 두는 것은 **넷 중 하나가 아직 열려 있어서**다 — 아래
「정할 것 넷」의 4(탈퇴 시 연결 해제). nonce(3번)는 같은 날 양쪽에 붙였다.

#### 어떻게 닫혔나 — **FE 제안보다 나은 답이 왔다**

FE 는 요청을 `{ identityToken, authorizationCode }` 로 제안하고 이름·이메일을
**선택 필드**로 얹자고 했다. 서버는 **`{ identityToken }` 하나만** 받는다 —
이름·이메일을 요청 본문이 아니라 **identity token 안의 클레임**에서 읽기 때문이다
(BE `AppleIdentityTokenVerifier.requireVerifiedEmail`).

⚠ **그래서 「배포를 막는 항목」이던 2번이 사라졌다.** 애플이 이름·이메일을 주는
것은 첫 인가 한 번뿐이지만, **identity token 의 `email` 클레임은 매번 온다** —
서버가 그쪽을 보므로 사용자가 언제 로그인하든 계정을 세울 수 있고, **태울 「첫
한 번」이 없다.**

✅ **실기기에서 확인했다** (2026-08-24). 재로그인이 `APPLE_EMAIL_UNAVAILABLE` 없이
통과한다 — 위 전제가 추론이 아니라 확인된 사실이다. `nonce` 왕복(SHA-256 hex)도
같은 기기에서 함께 확인했다.

✅ **그래서 릴리스 잠금을 지웠다.** `login.tsx` 의 `isAppleLineOpen` 이 사라졌고
애플 줄의 `disabled` 는 카카오와 같아졌다(2026-08-24).

⚠ **이름은 서버가 받지 않는다** — identity token 에 이름 클레임이 없기 때문이다.
막히지 않는다: 호칭은 온보딩 `04` 가 따로 받는다(`ARCHITECTURE.md` §1).

응답은 **카카오와 글자 그대로 같게** 왔다(FE 가 건 조건 · 아래 1번). 그래서 FE 는
응답 검증과 전송을 한 파일로 모아 두 공급자가 나눠 쓴다(`data/loginSession.ts`).

#### FE 는 어디까지 와 있나

| 단계                        | 상태                                                                    |
| --------------------------- | ----------------------------------------------------------------------- |
| 애플 시트 → credential 수신 | ✅ `src/features/auth/data/appleSdk.ts` (`expo-apple-authentication`)   |
| 서버 교환                   | ✅ `src/features/auth/data/appleAuthApi.ts` (`POST /api/v1/auth/apple`) |
| 세션 저장 · 라우팅          | ✅ 카카오와 **같은 코드**를 지난다 (`auth.ts` 의 `adoptSession`)        |

#### 정할 것 넷 — 셋 닫히고 하나 남았다

1. ✅ **경로와 요청 모양.** `POST /api/v1/auth/apple` · 요청 `{ identityToken }` ·
   응답은 카카오와 동일(`accessToken`·`refreshToken`·`tokenType`·
   `accessTokenExpiresIn`·`userId`·`onboardingRequired`). **`authorizationCode` 는
   보내지 않는다** — 서버가 읽지 않는다.
2. ✅ **이름·이메일을 서버가 받는가.** **토큰 클레임으로 받는다**(위 「어떻게
   닫혔나」). 이메일이 없거나 미인증이면 서버가 `400 APPLE_EMAIL_UNAVAILABLE` 로
   닫고, FE 는 그것만 **사용자가 할 일을 알려 주는 문구**로 띄운다(애플 ID 설정에서
   이메일 공유를 켜야 한다 · `auth.ts` 의 `APPLE_FAILURE_MESSAGES`).
   ⚠ 이메일이 **가림 주소**(`...@privaterelay.appleid.com`)일 수 있다는 점은 그대로다 —
   서버가 그 값을 카카오 이메일과 같은 칸에 넣는다면 「사람에게 닿는 주소」라는
   전제가 깨진다. **BE 쪽에 남은 확인 항목이다.**
3. ✅ **`nonce` 를 검증한다** (2026-08-24 · **양쪽을 같은 날 붙였다**). 규약은
   애플 권고대로 **애플에는 해시, 서버에는 원문**이다:

   ```
   raw    = 무작위 32바이트의 hex   → 요청 본문의 `nonce` (서버로)
   hashed = SHA-256(raw) 의 hex     → signInAsync({ nonce })  (애플로)
   ```

   애플이 그 해시를 토큰의 `nonce` 클레임에 그대로 넣어 주므로, 서버는 받은 원문을
   해시해 클레임과 맞춘다(BE `AppleIdentityTokenVerifier.requireMatchingNonce`).
   **인코딩은 양쪽 다 소문자 hex** — 갈리면 항상 불일치라 로그인이 통째로 막힌다.
   불일치·클레임 없음은 `401 APPLE_NONCE_MISMATCH` 이고, FE 는 그것을
   `apple_nonce_mismatch` 로 따로 이름 붙인다(정상 흐름에서는 나올 수 없는 값이라,
   반복되면 공격이 아니라 우리 규약이 틀린 것이다).
   ⚠ **클레임이 없는 토큰도 거절한다** — 「검사할 수 없으면 통과」는 검사를 없앤 것과 같다.
   ⚠ **막지 못하는 것**: 요청 하나를 통째로 가로챈 상대는 토큰과 원문을 함께 갖는다.
   그 창을 닫는 것은 HTTPS 이고 개발 서버는 아직 평문이다(§1-6) — nonce 는 그 대체재가 아니다.

4. ⛔ **탈퇴 시 애플 연결 해제 — 그대로 열려 있다.** 카카오는
   `DELETE /api/v1/users/me` 가 카카오 unlink 까지 한다(`withdrawApi.ts` 의 `kakao`
   실패 코드). 애플도 같은 의무가 있다 — App Store 심사 규정이 **앱 안에서 계정
   삭제**를 요구하고, 애플로 가입한 사용자는 서버가 애플에 `revoke` 를 보내야
   연결이 끊긴다. 서버가 `.p8` 로 서명해야 하는 일이라 **FE 가 할 수 있는 부분이
   없다.** §1-5 와 함께 본다.
   ⚠ **이제 애플로 가입한 사용자가 실제로 생긴다** — §1 에서 애플 관련으로 **유일하게 남은 항목**이다.
   ⚠ 붙이려면 계약이 한 줄 는다: 서버가 `authorizationCode` 를 받아 애플 refresh
   token 으로 바꿔 **저장해 두어야** 연결을 끊을 수 있다(스키마 변경 · `.p8` 필요).

#### 서버에 필요한 값

`.p8` · Key ID · Team ID 는 **백엔드로 간다**(`SETUP.md` 「등록 체크리스트」).
FE 는 아무 키도 들지 않는다 — 애플은 **번들 ID**(`kr.momentory.app`)로 앱을
알아본다. 서버는 identity token 의 `aud` 가 그 값인지 검증한다.

⚠ **서버의 `APPLE_CLIENT_ID` 가 그 번들 ID 와 같아야 한다.** 어긋나면 서버가
`401 APPLE_CLIENT_ID_MISMATCH` 를 내고, FE 는 그것을 **따로 이름 붙여** 둔다
(`apple_client_mismatch`) — 사용자 문구는 다른 401 과 같지만, 실기기에서 이 값이
돌아오면 「애플이 거절했다」가 아니라 **「배포 설정이 틀렸다」**를 봐야 하기 때문이다.

#### 구글은 아직 이 절에 없다

구글 로그인은 SDK 도 붙지 않았다(`S1` 의 구글 줄은 여전히 개발 통로다).
계약 질문이 같은 모양으로 생기겠지만, **애플이 먼저인 이유**는 iOS 빌드가
Sign in with Apple 없이는 심사를 통과하지 못하기 때문이다(심사 규정 4.8).
