# 캘린더 측정 — 무엇을 재고, 무엇이 아직 비어 있나

기기 캘린더에서 **무엇을 가져올지 정하려면 값을 재봐야 한다.** 이 문서는 그
측정의 **절차·항목·결과**를 한 곳에 둔다. 규칙의 정본이 아니다 — 정해진 규칙은
`src/lib/calendar.ts` 와 [`DISCUSSION.md`](DISCUSSION.md) §1-4 로 간다.

## 왜 재는가 — 타입은 값을 말해주지 않는다

`expo-calendar` 의 타입 정의는 **필드가 있다**까지만 말한다. 그 필드가 실제로
무엇을 담는지, 계정 종류마다 채워지긴 하는지는 **말하지 않는다.** 이미 한 번
어긋난 것을 봤다:

```
타입    instanceId?: string
실기기  instanceId: 1626        ← 숫자다
```

그래서 `allowsModifications` 가 `boolean` 이라는 사실만으로 「공휴일 달력을
갈라낸다」고 가정할 수 없다. **재야 안다.**

## 무엇을 정하려고 재는가

> **홈에 「광복절」이 뜨면 안 된다.** 2026-08-11 Android 실측에서 1년치 80건 중
> **46건(58%)이 공휴일 달력**이었다. 개인 일정은 29건뿐이다.

가르는 축은 **일정이 아니라 달력**이다. 「종일인가」로는 안 갈린다 — 「광복절」도
종일이고 「내 휴가」도 종일이라, 종일을 빼면 사용자가 적어둔 일정이 함께 사라진다.

찾는 것: **「내가 만든 일정이 아닌 달력」을 가려내는 신호.**

## 값과 무관하게 이미 정해진 뼈대

측정 결과가 어떻게 나오든 아래는 바뀌지 않는다. 먼저 못박아 두는 이유는, 값이
애매할 때 그때그때 정하면 플랫폼마다 다른 규칙이 생기기 때문이다.

1. **블랙리스트다. 화이트리스트가 아니다** — 「이건 구독/생일 달력이다」가 확실할
   때만 뺀다. 「이건 개인 달력이다」를 증명하려 들면, 신호가 비는 플랫폼에서
   **사용자 일정이 통째로 사라진다.**
2. **애매하면 포함한다** — 틀렸을 때 잃는 것이 작은 쪽으로 실패시킨다. 잘못 넣으면
   줄이 하나 더 보일 뿐이고, 잘못 빼면 사용자가 적어둔 일정이 없어진다.
3. **신호 하나를 믿지 않는다** — 여러 신호의 OR 로 판정한다. 플랫폼·계정마다
   채워지는 필드가 다르다.
4. **판정은 `src/lib/calendar.ts` 안에서만** — 화면·store 는 플랫폼을 모른다.
5. **자동은 최종형이 아니다** — 아무리 잘 맞아도 누군가에겐 틀린다(업무 달력을
   구독으로 쓰는 사람). `M1` 연결 관리에서 달력을 끄고 켜는 것이 최종 안전망이고,
   시안에 없어 상류 확인이 필요하다.

## 재는 항목

### ① 달력(`getCalendars(EntityTypes.EVENT)`)

**이게 이번 측정의 본론이다.** 달력마다 아래를 찍고, **개인 달력과 구독/생일
달력 사이에서 값이 갈리는지**를 본다.

| 필드                    | 왜 보나                             | Android                                     | iOS |
| ----------------------- | ----------------------------------- | ------------------------------------------- | --- |
| `title`                 | 어느 달력인지 사람이 알아보려고     | ✅ 측정                                     | ⬜  |
| `allowsModifications`   | **1순위 후보** — 구독이면 `false`?  | ✅ **갈린다 — 주 신호가 됐다**              | ⬜  |
| `type`                  | `subscription`·`birthday` 로 오는가 | ✅ **키 자체가 없다** — iOS 전용            | ⬜  |

| `ownerAccount`·`source` | 계정 종류로 갈리는가                | ✅ **부분만** — 삼성 공휴일을 못 잡는다     | ⬜  |
| `isVisible`             | 사용자가 캘린더 앱에서 끈 달력      | ✅ 4개가 `false` — 성격이 다른 신호다       | —   |

### iOS — 미측정

기기가 없어 아직이다. **다를 것으로 보는 곳:**

- `accessLevel`·`isSynced`·`isVisible` 이 **없다**(Android 전용) → 그만큼 신호가 준다

## 어떻게 재는가

측정은 **임시 프로브**로 한다. `src/lib/__calprobe.ts` 를 만들어 `app/index.tsx` 의
`useEffect` 에서 한 줄로 부르고, **확인이 끝나면 둘 다 지운다**(커밋하지 않는다).

```bash
# 1. USB 를 먼저 쓴다 (개발자 옵션 → USB 디버깅 → 폰 팝업에서 「항상 허용」)
adb devices -l
# 무선 디버깅은 망이 기기 간 통신을 막으면(사내·센터 WiFi) 안 된다.
# 페어링 창을 새로 열어도 그 포트에 TCP 가 안 닿으면 그 경우다 — 케이블이나 폰 핫스팟으로 간다.
adb pair <IP>:<페어링포트> <6자리>      # 처음 한 번만
adb connect <IP>:<연결포트>

# 2. 네이티브 모듈이라 dev client 재빌드가 필요하다
#    (JS 만 고칠 때는 재빌드 없이 Metro 로 충분하다 — 프로브 회차가 그렇다)
npx expo prebuild --platform android    # android/local.properties 가 지워지면 SDK 경로를 다시 넣는다
cd android && ./gradlew assembleDebug -PreactNativeArchitectures=arm64-v8a   # ~9분
#   ⚠ 실기기는 arm64 다. 플래그 없이(또는 x86_64 로) 빌드한 APK 는
#     INSTALL_FAILED_NO_MATCHING_ABIS 로 튕긴다 — 에뮬레이터용과 서로 덮어쓴다
adb install -r app/build/outputs/apk/debug/app-debug.apk

# 3. Metro 를 띄우고 앱을 그쪽으로 연다
npx expo start --dev-client --port 8081
adb reverse tcp:8081 tcp:8081
adb shell am start -a android.intent.action.VIEW \
  -d "momentory://expo-development-client/?url=http%3A%2F%2F127.0.0.1%3A8081" kr.momentory.app

# 4. 로그
adb logcat -d -s ReactNativeJS:* | grep CALPROBE
```

프로브는 **필드를 골라 찍지 않는다** — 달력·이벤트 **원시 객체를 통째로** 찍는다.
타입이 값을 말해주지 않는 것이 이 문서의 전제이므로, 고를 필드를 미리 안다고 가정할 수
없다(실제로 `type` 은 Android 에 **키 자체가 없었고**, 골라 찍었다면 `undefined` 하나로
끝나 「값이 안 온 것」인지 「필드가 없는 것」인지 갈리지 않았다).

한 회차에서 결정까지 닫으려면 아래 넷을 같이 찍는다:

1. 달력 원시 객체 + 이벤트 원시 객체 표본(달력마다 하나)
2. 달력별 건수 · 이벤트 필드 값 분포(`status`·`availability` 가 **채워지긴 하는지**)
3. `date+title` 중복 쌍
4. **후보 규칙별 「빠지는 달력 · 빠지는 건수 · 남는 건수」와 남는 일정의 제목 목록** —
   값만 봐서는 규칙이 맞는지 모른다. 남은 제목을 눈으로 봐야 안다

> ⚠ `logcat` 은 긴 줄을 자른다. 한 줄을 3000자로 끊어 여러 줄로 찍는다.
> ⚠ 타입에 없는 필드를 읽어야 하므로 **`Record<string, unknown>` 으로 뚫는다.**

## 판정 기준 — 어떤 결과면 무엇을 하나

| 측정 결과                                      | 그러면                                                         |
| ---------------------------------------------- | -------------------------------------------------------------- |
| 어떤 신호 하나가 개인/구독을 **깨끗이 가른다** | 그 신호로 필터를 만든다. 코드 몇 줄                            |
| 여러 신호가 **부분적으로** 가른다              | OR 로 묶는다(뼈대 3). 못 걸러지는 달력은 남는다                |
| **아무것도 안 갈린다**                         | 자동 필터를 포기하고 **사용자 선택**으로 간다 → 상류 확인 필요 |

어느 경우든 **뼈대 1·2·4 는 그대로**다.

## 결정 — 무엇을 보내고 무엇을 거르나 (2026-08-14)

위 표의 **첫 줄에 걸렸다** — 신호 하나가 깨끗이 갈랐다.

### 1. 거르는 규칙 · 달력 축 — 블랙리스트

```
읽지 않는다 (OR)
  isSynced === false                       ← 이미 있던 것. 기기에 안 내려온 달력
  allowsModifications === false            ← 주 신호. 두 OS 공통
  accessLevel ∈ { read, none, freebusy }   ← Android 전용. 위와 완전 중복이지만 남긴다(뼈대 3)
  isVisible === false                      ← Android 전용. 사용자가 캘린더 앱에서 끈 달력
```

- 앞의 셋은 **「내가 쓸 수 없는 달력이다」** 를 말한다. `isVisible` 만 성격이 다르다 —
  자동 판정이 아니라 **사용자가 이미 내린 결정**이다(「가족」 달력이 그 예: owner 인데 꺼져 있다)
- 값이 없는 플랫폼에서는 `undefined !== false` 라 **그냥 통과한다** — iOS 에서 신호가
  비면 그 달력은 보인다(뼈대 2)

### 2. 거르는 규칙 · 이벤트 축

```
제목이 빈 것             ← 실측 0건이지만 유지. 홈에 빈 줄을 만들지 않는다
status === "canceled"    ← 그 값일 때만. null 은 포함한다
접은 날짜가 창 밖
```

`status` 는 삼성·로컬 달력이 `null` 로 준다(14/23). 그래서 **「`confirmed` 만 남긴다」로
뒤집어 쓸 수 없다** — 그러면 본인 일정 10건이 통째로 사라진다.

**거절한 초대는 아직 못 거른다** — `expo-calendar` 가 이벤트에 참석 상태를 주지 않는다. 포함(뼈대 2).

### 3. 쓰지 않기로 한 신호 — 이유와 함께

| 신호                       | 왜 안 쓰나                                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `type`                     | Android 원시 객체에 **키가 없다.** iOS 전용                                                                           |
| `source.type` 화이트리스트 | ⛔ **위험.** `Samsung Calendar`(`com.osp.app.signin`)를 날렸다 — 본인의 쓰기 가능한 달력이다                          |
| `ownerAccount` 패턴        | 구글 공휴일(`…#holiday@group.v…`)만 잡고 삼성(`local.samsungholiday`)은 못 잡는다. `accessLevel` 이 이미 둘 다 잡는다 |
| `allDay`                   | 축이 아니다 — 「광복절」도 종일, 「경주」도 종일                                                                      |
| `availability`             | 갈리지 않는다 — 구글 공휴일은 `free`, 삼성 공휴일은 `busy`                                                            |

### 4. DB 로 보내는 값 — 이벤트당 셋

```
POST /api/v1/schedules/sync
  { from: "2026-07-01", to: "2026-09-30",
    events: [ { externalId, date, title }, … ] }
```

| 필드         | 값                                   | 예                         |
| ------------ | ------------------------------------ | -------------------------- |
| `externalId` | `` `${event.id}@${date}` ``          | `"951@2026-07-01"`         |
| `date`       | `YYYY-MM-DD` · **04:00 경계로 접음** | `"2026-07-01"`             |
| `title`      | `trim()`                             | `"오후 4시 캡스톤 팀미팅"` |

`source: "calendar"` 는 **이벤트마다 실어 보내지 않는다** — 이 엔드포인트로 들어온 것에
서버가 붙인다. `hidden` 은 서버가 들고 upsert 때 보존한다(`DISCUSSION.md` §1-4).

> ✅ **2026-08-21 — 서버 구현을 직접 읽고 대조했다**(BE `40da034` ·
> `ScheduleService.syncCalendar` · `Schedule.syncFromCalendar` · 마이그레이션 `V4`·`V15`).
> 위에 적어 둔 것이 전부 맞다. 문서에 없던 것 넷을 더한다:
>
> - **`(user_id, external_id)` 는 DB UNIQUE 다**(`uk_schedules_user_external_id`) —
>   `externalId` 를 이벤트 회차마다 갈라 둔 것(`${event.id}@${date}`)이 여기서 값을 한다.
>   **한 요청에 같은 `externalId` 가 두 번 들어오면 `400 INVALID_REQUEST`** 다
> - **삭제는 소프트 삭제**(`deleted_at`)이고, **되살아난다.** 기기에서 지웠다가
>   같은 `externalId` 로 다시 만든 일정은 **감정·마침·숨김을 그대로 되찾는다**
>   (`syncFromCalendar` 가 `deletedAt` 을 `null` 로 되돌린다). ⚠ **일정 하나를 지웠다
>   되돌리면 기록도 함께 돌아온다** — §1-4 가 경고한 「감정·마침이 함께 사라진다」의
>   반대편이고, 사용자에게 더 나은 쪽이다. 다만 어디에도 안 적혀 있었다
> - **`displayOrder` 는 서버가 매긴다** — 새로 만든 캘린더 일정은 그 날짜의 기존 일정
>   **뒤**에 붙는다(`date` → `title` → `externalId` 순으로 정렬해서 넣는다). 기기 캘린더의
>   순서를 따라가지 않는다
> - **`source = MANUAL` 인 행에는 `external_id` 를 못 넣는다**(CHECK 제약 ·
>   `chk_schedules_source_external_id`). 수동 일정이 화해에 휩쓸릴 길이 스키마 수준에서 막혀 있다

**기간은 첫 연결과 이후 화해 모두 「이전 달 1일 ~ 다음 달 말일」** 이다(8월이면 `07-01 ~ 09-30`).

- §1-4 「삭제는 보낸 범위 안에서만」이 그대로 걸린다. **창 밖으로 밀려난 과거는 서버에서
  굳는다** — 기기에서 지워도 안 지워진다. 이건 버그가 아니라 §1-4 가 경고한 대가
  (「감정·마침 기록이 함께 사라진다」)를 **최근 3개월로 가두는** 쪽의 선택이다
- 실측 페이로드: 23건 → 필터 후 **13건**(멀티데이를 펼치면 18건). 크기는 문제가 아니다

### 5. 보내지 않는 것 — 명시한다

시각(`startDate`·`endDate` 의 시:분) · `location` · `notes` · `alarms` · 참석자 ·
`organizerEmail` · **달력 이름·계정·색** · `calendarId` · `instanceId` · `recurrenceRule` · `allDay`.

이유가 둘이고 둘 다 무겁다:

- **`09.md` 규칙 1** — 「안내는 실제 처리와 같은 말이어야 한다」. 안내 카드가 약속하는 것은
  **일정 제목**뿐이다. `location`·`notes` 를 올리면 안내가 거짓이 된다(이 규칙 때문에
  이전 문구가 이미 한 번 폐기됐다)
- **달력 이름·계정은 그 자체로 개인정보다** — 올리면 사용자의 구글 계정 4개가 서버에 남는다.
  그리고 **없어도 `M1` 연결 관리는 된다**: 끈 달력은 다음 화해 목록에서 빠지고 서버가 창
  안에서 지운다. 필드를 안 늘리고 닫힌다

> 실측 부산물: 사용자는 **제목에 시각을 적는다**(`오후 4시 캡스톤 팀미팅` ·
> `10시 박주형멘토님 멘토링` · `오후 2시 입대 신청`). 시각을 안 읽어도 제목이 그것을
> 나른다 — `09.md` 의 「시간을 읽지 않는다」가 화면에서 덜 아픈 이유다.

### 6. 날짜를 정하는 규칙 — 종일 일정의 끝은 배타적이다

`광복절`이 `2026-08-15T00:00:00Z ~ 2026-08-16T00:00:00Z` 로 온다. **하루짜리다.**
마지막 날은 `endDate - 1일` 이다. 이 보정이 없으면 **모든 공휴일·생일이 이틀이 된다.**

종일 일정의 `startDate` 는 **UTC 자정**이고, KST(+9)에서 09:00 이 되어 `dayFrom` 이 같은
날로 접는다 ✅. ⚠ 기기 시간대가 UTC 서쪽이면 하루 밀린다 — MVP 는 국내만 보므로 받아들이고
여기 적어 둔다.

### 7. 반복 일정·연속 일정 — **하루에 한 줄로 편다** (2026-08-14 결정)

기기 일정 하나가 **DB 줄 여러 개**가 된다. 날짜마다 하나씩이다.

```
기기 캘린더        DB
"제주 여행"        8/1 제주 여행
8/1 ~ 8/5(배타) →  8/2 제주 여행
                   8/3 제주 여행
                   8/4 제주 여행
```

**왜 하루 단위인가:**

- 앱은 `date = 오늘` 로 하루치를 꺼내 보여준다. 8/3 줄이 없으면 **여행 3일차 홈이 빈다**
- **감정과 마침 표시가 줄마다 붙는다.** 한 줄이면 2일차 감정과 3일차 감정을 따로 남길 수 없다.
  회고가 하루 단위인 이상 일정도 하루 단위여야 한다

**둘이 갈린다 — 누가 펴는가:**

|                             | 누가                                                           | 우리가 할 일           |
| --------------------------- | -------------------------------------------------------------- | ---------------------- |
| **반복 일정**(매주 회의)    | **OS 가 편다** — `listEvents` 는 규칙이 아니라 **회차**를 준다 | 없다. 받은 대로 넣는다 |
| **연속 일정**(3박 4일 여행) | **아무도 안 편다** — 시작·종료를 가진 한 덩어리로 온다         | **우리가 편다**        |

반복 일정에 손댈 것이 없다는 게 중요하다 — **서버도 앱도 「반복」이라는 개념을 몰라도 된다.**
`externalId` 가 `id@date` 라서 회차든 연속 일정의 이틀째든 **자동으로 서로 다른 키**가 된다.

> 연속 일정을 안 펴면 어떻게 깨지는지: `9/30~10/6` 워크숍을 한 줄로 넣으면 DB 에 `9/30` 만
> 남는다. 10/3 에 앱을 열면 `date=10/3` 조회가 **빈손으로 온다** — 워크숍 중인데 홈이 비어 있다.

### 8. 창 경계 — 밀리면서 채워진다

창이 `7/1~9/30` 일 때 `9/30~10/5` 일정은 **`9/30` 한 줄만 들어간다.** 나머지는 창 밖이다.
그래도 비지 않는다 — 10월이 되면 창이 `9/1~11/30` 으로 밀리고 그때 `10/1~10/5` 가 채워진다.
앱은 「오늘」만 보므로 **미리 넣어 둘 필요가 없다.**

여기 딸려 오는 것 둘:

- **화해는 첫 연결만이 아니다.** 앱을 열 때마다 같은 규칙으로 돈다. 온보딩 때 한 번 넣고
  끝이면 10월 일정도, 사용자가 새로 적은 일정도 **영영 안 들어온다** — 3개월치가 박제된다.
  「첫 연결 = 3개월」이 아니라 **「항상 3개월, 첫 연결이 그 첫 실행」** 이다
- **순서가 있다 — 화해 먼저, 하루치 조회는 그다음.** 나란히 부르면 10/1 첫 실행에서 아직 안
  들어간 그날 일정을 조회하게 되어 **홈이 잠깐 빈다**

### 9. 같은 날 여러 일정의 순서 — **들어온 순서** (2026-08-14 결정)

**시각으로 정렬하지 않는다.** FE 가 읽은 순서 그대로 보내고, 서버가 새로 넣을 때
`displayOrder` 를 매긴다(이 필드는 `ScheduleResponse` 에 **이미 있다**). 화해가 다시 돌아도
**이미 있는 줄의 순서는 안 바꾼다.**

시각으로 정렬하려면 시각을 읽어야 하고, 그러면 `09.md` 「시간을 읽지 않는다」와 부딪힌다.
정렬 하나 때문에 그 약속을 흔들지 않는다.

> 대가: **하루 안에서 아침 일정이 저녁 일정 아래로 갈 수 있다.** 특히 나중에 추가된 일정은
> 시각과 무관하게 맨 뒤에 붙는다. 홈은 하루 최대 2건(실측)이라 지금은 눈에 띄지 않는다.

### 10. 언제·어떻게 화해하는가

**매번 그 창의 전량을 보낸다.** 「바뀐 것만」은 세 겹으로 막혀 있다:

|               | 막는 것                                                                                                                                                                                                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **변경 시각** | 타입에는 `lastModifiedDate` 가 **있는데** 2026-08-14 실측 원시 객체에는 **키 자체가 없었다.** `type` 필드 때와 같은 함정이다. iOS EventKit 에는 있을 가능성이 높은데, 그러면 **플랫폼마다 다른 동기화 규칙**이 생긴다                                                               |
| **변경 알림** | OS 에는 있다(Android `ContentObserver` · iOS `EKEventStoreChanged`). 그런데 **`expo-calendar` 가 내보내지 않는다** — 쓰려면 네이티브 모듈을 두 플랫폼에 직접 짜야 한다. 게다가 그 알림도 **「뭔가 바뀌었다」까지만** 말하고 무엇이 어떻게인지는 안 준다. 받고 나서 결국 전량 조회다 |
| **삭제**      | ⛔ **원리적으로 안 보인다.** 지워진 행은 그냥 없어진다(Android 는 sync adapter 에게만 `DELETED` 를 보여준다). 변경분만 받으면 **지운 것을 영영 모른다** — `DISCUSSION.md` §1-4 가 이미 같은 이유로 「추가」가 아니라 「화해」에 도달했다                                            |

세 번째가 결정적이다. 앞의 둘이 풀려도 삭제 때문에 어차피 전량 비교로 돌아온다.

비싸지 않다. 실측에서 달력 13개 × 3개월을 읽는 데 **0.2초**, 보낼 것은 **13건(약 1KB)** 이다.

**언제 도는가** — 네 자리다:

| 시점                             | 왜                                                      |
| -------------------------------- | ------------------------------------------------------- |
| `09` 에서 권한을 허용한 직후     | 첫 적재                                                 |
| 앱 콜드 스타트                   | 껐다 켠 사이의 변경                                     |
| **백그라운드 → 포그라운드 복귀** | **캘린더 앱에 일정을 적고 돌아온 직후가 바로 이것이다** |
| 04:00 하루 경계를 넘었을 때      | 창이 밀린다                                             |

**언제 보내지 않는가 — 이것이 안전장치다:**

> ⛔ **「못 읽었다」와 「0건이다」를 구별하지 못하면 서버가 전멸한다.**
> `readDeviceEvents` 는 권한이 없어도 조회가 실패해도 **빈 배열**을 준다(던지지 않는 것이 설계).
> 그 빈 배열을 화해에 그대로 실으면 서버는 「기기에서 다 지웠구나」로 읽고 **3개월치를 지운다** —
> 거기 붙은 감정·마침 기록까지 함께.
>
> 그래서 화해 경로는 **성공/실패를 구별해 돌려주는 통로**가 따로 필요하다
> (`{ ok: true, events } | { ok: false }`). `ok: false` 면 **한 건도 보내지 않는다.**
> 사용자가 설정에서 권한을 껐다가 다시 켜는 것이 실제로 일어나는 경로다.

**실패하면 조용히 넘어간다.** 캘린더는 앱의 본체가 아니라 회고 재료를 거드는 것이다(`RULES.md` 4).
**아웃박스(M3-3)도 필요 없다** — 화해는 멱등이라 다음 실행이 같은 것을 다시 보내면 그만이다.
재시도 큐를 만들 이유가 없다.

**나중에 네트워크를 아끼려면**(지금은 불필요): 읽은 목록을 정규화해 해시를 만들고, 지난번과
같으면 호출을 생략한다. 저장이 필요하므로 MMKV(M3) 뒤의 일이고, 그때도 **하루 한 번은 무조건
보낸다** — 서버 쪽이 어긋났을 때 되돌릴 길을 남겨 둔다.
(2026-11-06 대조: MMKV 를 기다리지 않고 **SecureStore 로 이미 했다**(`syncStateStore.ts` · 아래 「남은 것」).
⚠ 「하루 한 번은 무조건」은 **들어가지 않았다** — 해시와 범위가 같으면 늘 건너뛰고, 범위는 달이 바뀔 때만 바뀐다
(`calendarSync.ts`). 서버가 어긋나면 기기 캘린더가 바뀌거나 다음 달이 될 때까지 되돌아오지 않는다.)

이것이 **네이티브 델타 동기화 대신 쓰는 절충**이다. 기기에서 읽는 것은 0.2초라 어차피 싸고,
아끼려던 것은 결국 서버 왕복이었다. 0.2초를 더 아끼자고 플랫폼별 네이티브 모듈을 둘 떠안는
것은 남는 장사가 아니다.

### 11. 달력 사이 중복 — **접는다** (2026-08-14 결정)

**서로 다른 달력에 같은 `date`+`title` 이 있으면 한 줄로 합친다.** 남길 `externalId` 는
**사전순 최솟값**이다(달력 순서가 바뀌어도 같은 것을 남기려고).

실측에서 중복이 4쌍 나왔는데 성격이 갈린다:

|                          | 어디서                                                        | 공휴일 필터 뒤                                    |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------- |
| 3쌍 (제헌절·광복절·추석) | 삼성 「공휴일」 + 구글 「대한민국의 휴일」                    | **둘 다 통째로 빠진다** — 접기가 필요 없다        |
| 1쌍 (`생일 축하합니다!`) | 사용자의 구글 계정 **둘**이 같은 연락처 생일을 각자 들고 있다 | **둘 다 남는 개인 달력이다** — 이것 때문에 접는다 |

접어도 **사라지는 정보가 없다** — 줄 하나로 합쳐질 뿐이다. 뼈대 2(「애매하면 포함」)가
지키려는 것은 *사용자 일정이 사라지는 것*인데, 여기서는 그 위험이 성립하지 않는다.

⚠ **같은 달력 안에서는 접지 않는다.** 한 달력에 같은 날 같은 제목이 둘이면 사용자가 진짜로
둘 만든 것일 수 있다(「점심 약속」 두 건).
