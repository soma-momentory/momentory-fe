## 나누는 축

컴포넌트 재사용 구조를 따라 가른다. 상류 문서가 이미 답을 줬다 —
**온보딩 채팅 = 회고 채팅**이 같은 틀이고, 홈·보관함·리포트·마이는 목록·카드 문법을 공유한다.

|                 | 담당 | 화면 | 성격                                |
| --------------- | ---- | ---- | ----------------------------------- |
| **축 A — 대화** |      | 25장 | 진입 2 · 온보딩 11 · 회고 12        |
| **축 B — 목록** |      | 15장 | 홈 5 · 보관함 6 · 리포트 1 · 마이 3 |

두 축이 갈라지는 지점은 **M2 부터**다. M1(공용 컴포넌트)까지는 순서가 있어서
갈라 봐야 서로를 기다린다 — 아래 M1 절의 병렬 구간만 나눈다.

## M1 — P0 컴포넌트 13종 + 테스트 기반

**여기가 앱 전체의 지렛대다.** 채팅 컴포넌트군 하나가 온보딩과 회고 두 축을 다 덮는다.

### M1-0 · 테스트 기반 — 가장 먼저, 혼자

```
Jest + @testing-library/react-native + jest-expo
npm run test          CI 에 test 단계 추가
```

**컴포넌트보다 먼저 한다.** 나중에 붙이면 그때는 테스트하기 어려운 구조가 이미 굳어 있다.
첫 테스트는 `ScreenBackground` 렌더 하나면 충분하다 — 배선이 되는지만 본다.

### M1-1 · 기본 3종 — 혼자 (M1-2·M1-3 을 막는다)

### 2026-08-09 · 토큰 갱신 (M2-1 잔여) — 닫혔다

BE 가 `POST /api/v1/auth/reissue` 를 이미 구현해 두었다(`RefreshTokenReissueController`) —
`DISCUSSION.md` §1-6 이 "계약 없음"으로 적어둔 것이 먼저 풀려 있었다. FE 를 그
계약에 붙였다.

```
{ "refreshToken": "..." }
  → 200 { accessToken, refreshToken, tokenType: "Bearer", accessTokenExpiresIn }
  → 401 REFRESH_TOKEN_INVALID | REFRESH_TOKEN_REVOKED | REFRESH_TOKEN_EXPIRED
```

- `src/features/auth/data/reissueApi.ts` — `kakaoAuthApi.ts` 와 같은 방어(런타임 검사·
  타임아웃·던지지 않음)로 위 계약 하나만 감싼다
- `src/features/auth/model/auth.ts` — `getAccessToken()` 이 만료를 보면 **호출부 모르게**
  먼저 갱신을 시도한다. `hydrate()` 도 같은 경로를 타서 콜드 스타트에 살아있는
  refresh token 을 죽은 것으로 잘못 판정하지 않는다. 갱신마저 실패해야
  fail-closed(`anonymous`)다
- **refresh token 은 회전한다** — 한 번 쓰면 서버가 폐기하므로, 동시에 여러 API 호출이
  만료를 보고 각자 재발급을 보내면 늦은 쪽이 `REFRESH_TOKEN_REVOKED` 로 튕긴다.
  `refreshInFlight` 하나로 전체 세션에 갱신은 한 번에 하나만 나가게 막는다

이제 `access-token-expiration`(현재 30분, `application.yml`)이 지나도 화면에 "로그인이
만료됐어요"가 뜨지 않는다 — refresh token 자체가 만료·폐기됐을 때만 그 문구를 본다.

### 2026-08-24 · 애플 로그인 — **끝까지 붙었다** (SDK + 교환 + nonce + 탈퇴 revoke)

`expo-apple-authentication`(SDK 57 · `~57.0.1`)을 붙이고 `S1` 의 애플 줄을 **개발
통로(가짜 세션)에서 떼어냈다.** 같은 날 **서버 교환까지 이었다** — 그 줄은 이제
실제 시트를 열고 **모멘토리 세션까지 만든다.** 릴리스 잠금도 지웠다.

**끝난 것:**

- `src/features/auth/data/appleSdk.ts` — 네이티브 경계 하나. `kakaoSdk.ts` 와 같은
  규약이다(**던지지 않는다** · 결과는 네 갈래: `credential`·`cancelled`·
  `unavailable`·`failed`)
- `auth.ts` 의 `signInWithApple` — 카카오와 **자물쇠(`signingIn`)를 나눠 쓴다.**
  두 줄을 번갈아 눌러도 시트는 한 번만 열린다
- `src/features/auth/data/appleAuthApi.ts` — **서버 교환**(`POST /api/v1/auth/apple`).
  보내는 것은 **`identityToken` 하나뿐**이다 — 서버가 이름·이메일을 토큰 안의
  클레임에서 읽는다. 거절은 애플의 이름으로 옮긴다(`apple_email_unavailable` ·
  `apple_token_invalid` · `apple_client_mismatch` · `apple_upstream` …)
- `appleSdk.ts` 의 nonce — `expo-crypto` 로 무작위 32바이트를 만들어 **해시는
  애플에, 원문은 credential 에** 담는다. 서버가 그 원문을 해시해 토큰 클레임과 맞춘다
- `src/features/auth/data/loginSession.ts` — **카카오와 나눠 쓰는 전송·응답 검증.**
  응답이 글자 그대로 같아서 모았다(§1-10 「정할 것 넷」1 이 건 조건이다).
  `kakaoAuthApi.ts` 는 이 위로 옮겨졌고 **공개 API·판정은 그대로다**
- `auth.ts` 의 `adoptSession` — 교환 뒤(저장 · 온보딩 플래그 · `authenticated` ·
  프로필 배웅)를 두 공급자가 나눠 쓴다. 공급자를 묻지 않는 일이다
- `app/(auth)/login.tsx` — 애플 줄이 `signInWithApple` 을 부른다. 세션이 생기면
  카카오와 **같은 곳으로** 보낸다(`onboardingRequired` 가 정한다).
  **옛 `isAppleLineOpen` 은 지웠다** — `disabled` 가 카카오와 같아졌다
- `app.config.ts` — `expo-apple-authentication` 플러그인. 하는 일은
  **엔타이틀먼트 하나**(`com.apple.developer.applesignin`)와
  `CFBundleAllowMixedLocalizations` 다. **키를 받지 않는다** — 애플은 번들 ID
  (`kr.momentory.app`)로 앱을 알아본다
- 테스트 — `appleSignIn.test.ts` 24(SDK 경계 + SDK→교환→저장 전 구간) ·
  `appleAuthApi.test.ts` 26(어댑터 계약) · `login.test.tsx` 4

**교환이 어떻게 닫혔나 — 서버가 FE 제안보다 나은 답을 냈다.**

FE 는 요청을 `{ identityToken, authorizationCode }` + 이름·이메일 선택 필드로
제안했는데, 서버는 **`identityToken` 하나만** 받는다 — 이름·이메일을 요청 본문이
아니라 **identity token 안의 클레임**에서 읽기 때문이다(BE
`AppleIdentityTokenVerifier.requireVerifiedEmail`).

**그래서 릴리스 잠금이 사라졌다.** 잠가 두었던 이유는 「애플이 이름·이메일을 첫
인가 한 번만 주는데 받아 둘 서버가 없다」였다. 서버가 보는 `email` 클레임은
**매번 오므로** 태울 「첫 한 번」이 없다. `login.tsx` 의 `isAppleLineOpen` 을
지웠고, `login.test.tsx` 의 잠금 테스트는 **「빌드 종류로 갈리지 않는다」**로
뒤집어 고정했다(잠금이 조용히 되살아나면 심사 규정 4.8 이 요구하는 줄이 운영에서
눌리지 않는다).

⚠ **이름은 서버가 받지 않는다** — 토큰에 이름 클레임이 없다. 막히지 않는다:
호칭은 온보딩 `04` 가 따로 받는다. `appleSdk.ts` 는 `authorizationCode`·
`fullName`·`email` 을 계속 꺼내 오지만 **아무도 쓰지 않고 버린다** — 서버가
요구하게 되는 날 그 경계를 다시 열지 않으려는 것이다.

**`nonce` 도 같은 날 붙였다 — 양쪽이 함께**(`DISCUSSION.md` §1-10 의 3):

```
raw    = 무작위 32바이트의 hex   → 요청 본문의 `nonce` (서버로)
hashed = SHA-256(raw) 의 hex     → signInAsync({ nonce })  (애플로)
```

애플이 해시를 토큰의 `nonce` 클레임에 그대로 넣어 주므로 서버가 원문을 해시해
맞춘다(`AppleIdentityTokenVerifier.requireMatchingNonce`). **클레임이 없는 토큰도
거절한다** — 「검사할 수 없으면 통과」는 검사를 없앤 것과 같다. 불일치는
`401 APPLE_NONCE_MISMATCH` 이고 FE 가 `apple_nonce_mismatch` 로 따로 이름 붙인다
(정상 흐름에서는 나올 수 없어서, 반복되면 공격이 아니라 규약이 틀린 것이다).
⚠ **막지 못하는 것**: 요청을 통째로 가로챈 상대는 토큰과 원문을 함께 갖는다 —
그 창은 HTTPS 가 닫는다(§1-6 · 아직 평문). nonce 는 그 대체재가 아니다.

**탈퇴 시 애플 연결 해제도 붙었다** (`DISCUSSION.md` §1-10 의 4):

어려운 점은 **탈퇴 시점에 끊을 토큰이 없다**는 것이었다. 애플 revoke 는 refresh
token 을 요구하는데 그걸 얻으려면 authorization code 를 교환해야 하고, 사용자가
탈퇴 화면에서 Sign in with Apple 을 다시 하지는 않는다. 그래서 **로그인 때 미리
받아 둔다**:

```
로그인:  authorizationCode → POST /auth/token → refresh token → oauth_accounts 에 보관
탈퇴:    보관된 refresh token → POST /auth/revoke → 계정 삭제
```

FE 가 하는 일은 **요청에 `authorizationCode` 한 줄을 더하는 것뿐**이다 —
`appleSdk.ts` 가 이미 꺼내 오고 있어서 경계는 손대지 않았다. 선택 필드라 **없어도
로그인은 된다**(교환 실패가 로그인을 막지 않는다).

⛔ **`.p8` 이 아직 발급 전이다.** 설정이 없으면 로그인은 되고 **탈퇴만 지나간다**
(경고 로그를 남긴다) — 계정 삭제 자체도 심사 규정이 요구하는 기능이라 탈퇴를 통째로
막는 쪽이 더 나쁘기 때문이다. **운영 배포 전에 반드시 설정돼야 한다.**

**배포 순서가 있다 — BE 가 먼저다.** FE 릴리스가 서버보다 앞서면 애플 줄이
`404` 를 받아 「지금은 로그인할 수 없어요」로 닫힌다. 서버 쪽에 **`APPLE_CLIENT_ID`
(= 번들 ID `kr.momentory.app`)가 설정돼 있어야 앱이 부팅된다**(기본값 없는
`@NotBlank`) — 어긋나면 `401 APPLE_CLIENT_ID_MISMATCH` 다.

세 가지가 이 판단을 따라온다:

1. **가짜 세션으로 메우지 않았다.** 구글 줄은 여전히 `signInDev`(개발 빌드 전용
   가짜 세션)를 지나지만, 애플은 그 통로를 **쓰지 않는다** — 실기기에서
   엔타이틀먼트·번들 ID·콘솔 등록이 맞는지 확인할 경로가 이것뿐이라, 그 경로가
   진짜여야 한다
2. **`nonce` 는 인가마다 새로 만든다.** 재사용하면 막으려던 재생이 된다 —
   난수를 만들지 못하면 **시트를 열지도 않는다**(nonce 없는 credential 은 서버가
   어차피 거절한다)
3. **이름·이메일은 꺼내 오되 보내지 않는다.** 서버가 토큰 클레임에서 읽으므로
   요청 본문에 실을 이유가 없다 — 실으면 「보냈으니 저쪽이 갖고 있겠지」라는
   잘못된 전제가 생기고, 그 전제는 탈퇴 시 `revoke` 를 논할 때 어긋난다

**Android 에서도 같은 줄, 같은 코드다.** 애플 줄을 플랫폼별로 감추지 않는다 —
`Platform.OS` 를 화면에 적기 시작하면 같은 판정이 여러 곳에 생긴다. 대신
`appleSdk.ts` 의 `isAppleSignInAvailable()` 이 「이 기기에서 되는가」를 판정하고,
안 되면 **재시도를 권하지 않는 한 줄**로 닫는다(「이 기기에서는 애플 로그인을 쓸
수 없어요」) — 다시 눌러도 같기 때문이다.

⚠ **네이티브라 dev client 재빌드가 필요하다** — `npx expo prebuild` → `npm run ios`.
Android 빌드에는 아무 영향이 없다(플러그인이 iOS 만 건드린다).

✅ **실기기 검증 완료** (2026-08-24 · iOS 기기). 확인된 것 셋:

1. **시트가 뜨고 로그인이 끝까지 간다** — 엔타이틀먼트·번들 ID·콘솔 등록이 맞다
2. **`nonce` 왕복이 맞다** — 앱이 준 SHA-256 hex 가 토큰의 `nonce` 클레임으로 돌아오고
   서버 대조가 통과한다. 인코딩 규약(소문자 hex)이 양쪽에서 실제로 일치한다
3. ⭐ **재로그인도 된다** — 이것이 가장 불확실했던 지점이다. 애플이 이름·이메일을
   credential 로 주는 것은 첫 인가뿐인데, **identity token 의 `email` 클레임은 매번
   온다**는 전제 위에 서버 설계와 릴리스 잠금 해제가 얹혀 있었다. 두 번째 로그인에서
   `APPLE_EMAIL_UNAVAILABLE` 없이 통과해 그 전제가 사실로 확인됐다.

### 2026-08-10 · 로그아웃 — 서버의 refresh token 도 폐기한다

`POST /api/v1/auth/logout` 에 붙였다(요청 `{refreshToken}` → `204` 본문 없음, 오류
`400 INVALID_REQUEST`). **제출한 토큰 하나만 멱등적으로 폐기한다** — 다른 기기는 살아
있다. 그전까지는 기기에서만 지워서, 서버에 남은 refresh token 이 수명이 다할 때까지
새 access token 을 계속 발급받을 수 있었다.

- `src/features/auth/data/logoutApi.ts` — `reissueApi.ts` 와 같은 방어. **`lib/http.ts`
  를 지나지 않는다**: Bearer 를 쓰지 않고 refresh token 자체가 신원을 증명하는 계약이고,
  `authedRequest` 를 쓰면 `getAccessToken()` 이 만료를 보고 **폐기보다 먼저 재발급을
  보내** refresh token 이 회전해 손에 든 토큰이 그 자리에서 죽는다. 성공(204)의 본문은
  읽지 않는다 — 없는 것을 파싱하면 끝난 폐기가 실패로 보고된다
- `signOut` 은 **로컬을 먼저 비우고 폐기를 배웅으로 보낸다.** 기다리지 않으므로 서버가
  죽어 있어도 로그아웃은 즉시 끝난다 — **로그아웃은 실패할 수 없는 동작**이다.
  `SettingRow` 에 진행 중을 보일 자리가 없고 화면도 `void signOut()` 이라 기다릴 준비가
  안 돼 있다
- **비우는 store 를 넓혔다** — 온보딩 초안·완료 플래그 둘뿐이라 회고 대화·일기·프로필·
  알림 설정이 메모리에 남았다. 회고 대화는 서버가 그 사용자를 위해 생성한 문장 전문이라
  다음 사용자에게 남길 것이 아니다(`ARCHITECTURE §3-5`). 목록의 단일 지점은 `auth.ts`
  의 `clearUserScopedStores` 이고, MMKV·Query 캐시·아웃박스는 생기는 마일스톤에서 합류한다

남은 것: **회원 탈퇴** 시의 폐기 — 그 계정의 **모든 기기** 세션을 끊어야 하고
삭제 범위·유예가 아직 열려 있다(`DISCUSSION.md` §1-5 · §1-6). 확인 화면도 없다.

### 2026-08-10 · 갱신이 도는 사이 세션이 갈릴 때 (위 항목의 후속 — 닫힘)

로그아웃 직후 갱신이 끝나면 `performRefresh` 의 `persist()` 가 **지워진 세션을 다시
써넣었다** — 다음 부트에 조용히 로그인된 상태가 됐다. 반대 방향도 있었다: 로그아웃 뒤
다시 로그인했는데 앞 세션의 갱신이 거부로 끝나면 **갓 만든 새 세션을 지웠다.**

규칙 하나로 닫는다 — **갱신은 자기가 시작한 세션만 교체한다.** `swapSession` 이
기기에 있는 것이 아직 그 세션일 때만 쓰고(compare-and-swap), 거부로 지울 때도
`deleteIfUnchanged` 로 같은 것을 확인한다. 결과에 `stale` 을 더해 「세션이 갈렸다」를
「세션이 죽었다(`evicted`)」와 구분한다 — 안 그러면 남의 판정을 덧쓴다.

- **세대 카운터를 쓰지 않았다.** 갱신이 로그아웃 _이후에_ 시작하는 인터리빙(부팅 중
  `hydrate` 등)에서는 이미 올라간 번호를 들고 시작해 못 잡는다. 「저장된 값이 아직
  내 것인가」가 더 정확한 질문이다
- **회전한 토큰을 서버에 남기지 않는다** — 갈린 것을 알았을 때 방금 받은 refresh
  token 을 `orphanRevoke` 로 폐기한다. 로그아웃이 보낸 폐기는 그보다 앞선(이미 죽은)
  토큰을 가리켰으므로 이 한 장은 아무도 지우지 않는다
- ⚠ **읽기와 쓰기 사이 한 틱은 여전히 열려 있다** — SecureStore 에 원자적 교체가 없다.
  왕복(초 단위)이 마이크로태스크 몇 개로 줄어드는 것이 한계이고, 그 이상은 잠금이 필요하다

**테스트로 고정한 것**(5건, 고치기 전 코드에서 전부 실패): 로그아웃 뒤 갱신 성공이
세션을 되살리지 않는다 · 그때 새 refresh token 도 폐기한다 · 재로그인 뒤 갱신 성공이
새 세션을 덮지 않는다 · 재로그인 뒤 갱신 거부가 새 세션을 지우지 않는다 · 부팅 중
로그아웃하면 `hydrate` 가 `authenticated` 로 되돌리지 않는다.

### 2026-08-20 · `auth` ↔ `http` 순환 참조 — 지금은 두고, 근거만 적는다

에뮬레이터에서 dev client 를 띄우면 Metro 가 매번 이 경고를 낸다:

```
WARN Require cycle: src/features/auth/model/auth.ts
                 -> src/features/auth/data/meApi.ts
                 -> src/lib/http.ts
                 -> src/features/auth/model/auth.ts
```

`http.ts` 가 매 요청마다 `auth.ts` 의 `getAccessToken()` 을 읽고(토큰의 정본은
SecureStore 세션이므로 캐시하지 않는다), `meApi.ts` 는 다시 `http.ts` 를 지나기
때문이다 — **세 파일 각자의 규칙은 맞는데 셋이 모이면 고리가 된다.**

**지금 고치지 않는 이유**: 타입·테스트·실기기 전부 정상이고, 순환의 실제 위험인
「초기화 전 값 참조」가 일어나려면 모듈 로드 시점에 `getAccessToken` 을 불러야 하는데
`http.ts` 는 **함수 안에서만** 부른다. 즉 지금 구조에서는 터지지 않는다.

**그래도 적어 두는 이유**: 무해한 것이 아니라 **무해하게 유지되고 있는 것**이다.
누가 `http.ts` 상단에서 토큰을 한 번 읽어 상수로 두는 순간(캐싱은 자연스러운 유혹이다)
`undefined` 가 조용히 박힌다. 오류를 화면에 띄우지 않는 설계(규칙 5)라 그 사실은
「로그인이 가끔 풀린다」로만 드러난다.

**푸는 방법**: 토큰 접근자만 `src/lib/` 쪽 작은 모듈로 빼면 `http.ts → auth.ts`
간선이 사라진다. `auth.ts` 는 그 모듈에 쓰고, `http.ts` 는 그 모듈에서 읽는다.
급하지 않으므로 **인증 주변을 손대는 PR 이 생길 때 묶어서** 한다.
