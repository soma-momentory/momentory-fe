# 데이터 보안 — 기기에 무엇을 어떻게 눕히는가

> ⚠ **이 문서는 구현 계약이지 사용자 약속이 아니다.** 상류가 `S1` 에서 암호화
> 문구를 지웠다 — 「확정 범위가 아닌 약속을 화면에 쓰지 않는다」(`RULES.md`).
> **문서가 생겼다고 화면에 약속이 되살아나면 안 된다.** 여기 적힌 것이 사용자에게
> 보여도 되는 문장이 되려면 법률 검토(상류 `R-14`)와 §2 결정을 지나야 한다.

이 문서가 막고 있던 것: **MMKV 영속화**(M3 · 첫 로컬 쓰기). 일기 본문과 감정이
민감 필드라, 어디에 어떤 상태로 눕힐지 정하지 않고는 `react-native-mmkv` 를 깔 수
없었다([`DISCUSSION.md`](DISCUSSION.md) §2 · [`TASKS.md`](TASKS.md)).

**이 문서는 기기 쪽만 정한다.** 서버 보관·삭제는 BE 답이 필요해 아래 「아직 못
정한 것」에 남는다(§1-5).

---

## 1. 무엇이 민감한가 — 필드 네 등급

「민감」을 한 단어로 뭉뚱그리면 **전부 암호화하거나 아무것도 안 하게 된다.** 네
등급은 성격이 다르고, 등급이 곧 저장 위치를 정한다.

| 등급                  | 무엇                                                                                                                                                                                    | 왜                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **A · 세션 비밀**     | 모멘토리 access/refresh token                                                                                                                                                           | 유출되면 **남이 그 사람 계정으로 서버에 말한다.** 이미 SecureStore 에 있다                                            |
| **B · 자유 텍스트**   | `Diary.body` · `Diary.babaView` · `Retro.messages` · `Moment.text` · `ActionCard.{situation,targetAction,reflection}` · `Schedule.title` · 온보딩 「기타」 둘 · `Report.{insight,flow}` | **그 사람이 쓴 말 그대로다.** 일기 한 편이 새면 하루가 통째로 샌다. 회고 대화는 서버가 그 사람을 위해 생성한 문장이다 |
| **C · 감정·프로필**   | `Diary.emotions` · `Schedule.emotions` · `Retro.startEmotion` · `User.{ageBand,gender,interests,restMethods}`                                                                           | 본문은 아니지만 **묶으면 사람을 그린다.** 감정은 민감정보에 준해 다룬다(§2-2 대기)                                    |
| **D · 비민감 플래그** | `onboardingCompleted` · 마지막으로 본 주차 · 알림 스위치 · 캘린더 연결 여부                                                                                                             | 새어도 그 사람에 대해 말해주는 것이 없다. **암호화 비용을 여기 쓰지 않는다**                                          |

**`User.nickname` 은 B 가 아니라 C 다** — 본인이 정한 호칭이고 화면 곳곳에 뜬다.
다만 실명일 수 있으므로 **로그·계측에는 넣지 않는다**(3절).

## 2. 어디에 눕히는가 — 저장소 셋

```
SecureStore            A(세션 토큰) · MMKV 암호화 키                 ← OS 키체인/키스토어
MMKV "momentory.enc"   B · C                                        ← 암호화. 키는 위에서 온다
MMKV "momentory.cache" D                                            ← 평문. 지워져도 잃는 것이 없다
메모리(Zustand)         전부 — 위는 그 스냅샷이다
```

**진실은 언제나 서버이고, 기기의 것은 캐시다.** 그래서 기기 저장이 깨졌을 때
할 일은 「고치기」가 아니라 「버리고 다시 받기」다 — 아래 실패 규칙이 전부 그
전제 위에 있다.

### 2-1. 왜 MMKV 를 둘로 가르는가

한 통에 넣고 통째로 암호화하면 **비민감 플래그를 읽는 데도 키가 필요해진다.**
키를 못 읽는 상황(2-3)에서 `onboardingCompleted` 하나 때문에 진입 분기가 막히면,
사용자는 **답을 다 했는데도 온보딩을 다시 본다.** 등급 D 를 따로 두면 그 경로가
키와 무관해진다.

반대로 D 통에 B·C 를 얹지 않는다 — 「지금은 안 민감하니까」로 시작한 값이
나중에 본문을 물고 들어온다.

### 2-2. 암호화 키는 SecureStore 에 산다

```
32바이트 무작위 → base64 → SecureStore["momentory.mmkv.key"]
                              keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY
```

- **키를 코드·번들·서버에 두지 않는다.** 번들에 두면 APK 를 푼 사람이 그대로
  읽는다(`CONTRIBUTING.md` 「값을 다루는 세 등급」 ①의 교훈이 그대로 적용된다)
- **`THIS_DEVICE_ONLY` 다** — 기기 백업·기기 이전에 키가 따라가지 않는다. 새 기기는
  키가 없으니 옛 파일을 못 읽고, **서버에서 다시 받는다.** 이것이 우리가 원하는
  결과다: 기기를 옮기는 것은 복원이 아니라 재동기화다
- **`WHEN_UNLOCKED` 로 충분한 이유**: 잠긴 기기에서 도는 코드가 없다. 알림은 OS 가
  미리 예약해 두고 띄우므로(`lib/notifications.ts`) 우리 코드가 깨어나지 않는다.
  ⚠ 백그라운드 동기화·아웃박스 재생이 생기면 이 전제가 깨진다 —
  그때 `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` 로 내린다
- 키 생성은 `expo-crypto` 의 `getRandomBytesAsync` 다. **`Math.random()` 을 쓰지
  않는다** — 예측 가능한 키는 키가 아니다

### 2-3. 키를 못 읽으면 — **평문으로 떨어지지 않는다**

기기 오류·키체인 접근 실패·복호 실패는 실제로 일어난다. 그때 규칙:

1. **암호화 저장소를 열지 않는다.** B·C 는 그 세션 동안 **메모리로만** 산다 —
   앱을 끄면 사라지고, 다음 실행에 서버에서 다시 받는다
2. **평문 통(`cache`)에 대신 쓰지 않는다.** 「이번 한 번만」이 그대로 굳는다
3. **사용자에게 오류를 띄우지 않는다.** 할 수 있는 일이 없다(`RULES.md` 4).
   앱은 서버를 보며 그대로 돈다 — 느려질 뿐 멈추지 않는다
4. **개발 빌드에서만 사유를 남긴다** — 키 없음 · 복호 실패 · 저장소 열기 실패를
   가른다(`kakaoSdk.ts` 의 `warnInDev` 와 같은 자리). **값은 남기지 않는다**

같은 이유로 **손상된 암호화 통은 고치지 않고 비운다.** 부분 복호로 살린 데이터는
어디까지 진짜인지 아무도 모른다.

## 3. 로그·계측에 남기지 않는 것

이미 정본이 있다 — [`CONTRIBUTING.md`](CONTRIBUTING.md) 「값을 다루는 세 등급」과
[`ARCHITECTURE.md`](ARCHITECTURE.md) §6. 여기서는 저장 관점으로 한 줄만 덧붙인다:

**등급 B 는 어떤 형태로도 로그에 닿지 않는다.** 토큰·본문·자유 텍스트·닉네임.
감정은 **`emotion_id` 숫자만** 보낸다. 그래서 예외를 삼킬 때도 `error.message`
까지만 남기고 요청 본문은 남기지 않는다(`http.ts` · 각 어댑터의 `warnInDev`).

## 4. 지우기 — 로그아웃과 탈퇴

**목록의 단일 지점은 `auth.ts` 의 `clearUserScopedStores` 하나다**
(`ARCHITECTURE.md` §3-5). 새 저장소가 생기면 **그 함수에 합류**하는 것이 규칙이고,
이 문서는 그 목록이 무엇이어야 하는지를 정한다.

| 무엇               | 로그아웃 | 탈퇴 | 어떻게                                                          |
| ------------------ | -------- | ---- | --------------------------------------------------------------- |
| SecureStore 세션   | ✅       | ✅   | `deleteItemAsync` + 서버 refresh token 폐기(`logoutApi`)        |
| **MMKV 암호화 키** | ✅       | ✅   | 키를 지우면 **남은 파일은 복호 불가능한 바이트**가 된다         |
| MMKV `enc` 통      | ✅       | ✅   | `clearAll()` — 키 삭제만 믿지 않는다(아래)                      |
| MMKV `cache` 통    | ✅       | ✅   | `clearAll()`                                                    |
| 메모리 store 여섯  | ✅       | ✅   | 지금 이미 비운다                                                |
| 아웃박스 큐(M3-3)  | ✅       | ✅   | 남기면 **다음 사용자의 세션으로 이전 사용자의 쓰기가 재생**된다 |
| 예약된 알림        | ✅       | ✅   | `features/my/model/reminders.ts` 가 인증 상태를 보고 취소한다   |

**키만 지우고 파일을 남기지 않는다.** 「복호할 수 없으니 없는 것과 같다」는
맞지만, 남은 파일은 **용량으로 남고 포렌식 대상으로 남는다.** 둘 다 한다 —
`clearAll()` 이 실패해도 키가 없어 못 읽고, 키 삭제가 실패해도 내용이 없다.

**순서는 「비우고 나서 상태를 바꾼다」** — 로그아웃 판정이 먼저 서면 그 사이에
화면이 빈 store 를 읽고 그린다.

⚠ **우리가 보장할 수 없는 것**: OS 백업(iCloud·Google 백업)에 이미 올라간 사본,
파일시스템의 삭제 흔적. `THIS_DEVICE_ONLY` 키가 백업을 따라가지 않으므로
**백업본은 복호 불가**지만, 「완전히 지워졌다」고 말할 수는 없다.

> ⛔ **이 표는 「기기」의 목록이고, 서버는 이 중 한 줄도 지우지 않는다**
> (BE 코드 대조 · 2026-08-21). 지금 서버에서 일어나는 일은 하나뿐이다:
>
> - **로그아웃** — `POST /api/v1/auth/logout` 이 **제출한 refresh token 하나만**
>   폐기한다. 다른 기기의 세션은 살아 있고, 같은 토큰을 두 번 보내도 결과가 같다
> - **탈퇴** — **엔드포인트가 없다.** 사용자 삭제 경로가 BE 전체에 하나도 없어서,
>   위 표의 「탈퇴 ✅」는 **기기에서만 참**이다. 서버의 일기·회고·일정은 그대로 남는다
> - **「모든 기기 세션 끊기」도 없다** — 탈퇴에 필요한 그 동작을 서버가 아직 못 한다
>
> 그래서 **탈퇴 화면을 만들 때 문안을 여기서 가져다 쓰면 안 된다.** 지금 쓸 수 있는
> 문장은 「이 기기에서 지웁니다」까지다([`DISCUSSION.md`](DISCUSSION.md) §1-5 · §1-6).
> 마이의 「회원 탈퇴」 줄이 아직 눌리지 않는 것과 같은 이유다.

## 5. ⛔ 아직 못 정한 것 — 팀이 답해야 닫힌다

세 개다([`DISCUSSION.md`](DISCUSSION.md) §2). **FE 안을 함께 적었다** — §1-1
멱등성처럼, 안이 있으면 팀은 〈예/아니오〉만 답하면 된다.

### 5-1. `ageBand`·`gender` 를 정말 받을 것인가

지금: 온보딩 `05-b` 가 묻고 `M2` 가 편집하고 `PUT /users/me/onboarding` 으로
서버에 간다. **그런데 리포트·추천 어디에도 쓰이지 않는다.**

> **FE 안 — 받되 용도를 잠근다.** 최소수집 원칙의 기본값은 「쓰는 곳이 생길
> 때까지 묻지 않는다」이지만, 질문을 내리는 것은 상류 화면 결정이라 FE 가 못
> 한다. 대신 `05-b` 가 이미 화면에서 목적을 말하고 있다 — "답변은 질문을 조금 더
> 잘 맞추는 데만 사용하며, 다른 사람에게 공개되지 않아요." **그 문장을 그대로
> 계약으로 삼는다**: 회고 질문 생성 밖(통계·광고·추천 학습·외부 공유)으로 쓰지
> 않는다. 선택 항목이고 지우는 길이 `M2` 에 있다는 것도 이미 참이다.
>
> 팀이 「안 받는다」로 정하면 상류에 `05-b` 철회를 올린다 — 그때 지울 것은
> 화면 · `draft.ts` 둘 · 서버 필드 둘이다.

### 5-2. 감정 기록에 별도 동의를 받을 것인가

민감정보에 준하는 취급이고 법률 검토(상류 `R-14`)와 맞물린다. 지금 동의 절차는
없다.

> **FE 안 — 동의 화면을 새로 만들지 않는다.** MVP 상태 기계에 그 화면이 없고,
> 「갈 곳 없는 줄·화면을 만들지 않는다」가 규칙이다. 대신 지금 지킬 수 있는
> 것을 계약으로 못 박는다: 감정은 **계측에 숫자 id 로만** 나가고(3절), 기기에는
> 등급 C 로 암호화돼 눕고, 개인정보 처리방침이 감정 항목을 명시한다.
> `M3` 의 안내가 이미 그 방침을 가리킨다("기록 보호 방식은 개인정보
> 처리방침에서 확인할 수 있어요").
>
> 법률 검토가 「별도 동의 필요」로 나오면 **화면이 하나 생긴다** — 그건 상류
> 몫이고, 그때 이 절을 그 화면으로 대체한다.

### 5-3. 서버 보관 기간·탈퇴 삭제 보장

**BE 답이 필요하다**(§1-5). 알아야 하는 것: 서버 저장 암호화(at rest) 수준 ·
탈퇴 시 삭제가 즉시인지 유예인지 · 백업·로그에 남는 사본의 수명 · 회고 대화
전문의 보관 기간.

> **2026-08-21 · BE 코드에서 확인한 현재 상태** — 답이 아니라 **질문의 좌표**다:
>
> | 무엇                | 지금 서버                                                                                       |
> | ------------------- | ----------------------------------------------------------------------------------------------- |
> | 탈퇴 삭제           | **엔드포인트 자체가 없다.** 「즉시냐 유예냐」 이전 단계다                                        |
> | 일기 삭제           | **하드 삭제** — `DiaryService.delete` 가 행을 지운다                                            |
> | 일정 삭제           | **소프트 삭제** — `deleted_at` 만 찍고 행은 남는다(캘린더 화해가 지운 것도 마찬가지)             |
> | **회고 대화 전문**  | `retrospects.state_json` 에 **버블·답변·측정값이 통째로** 남는다(`RetrospectState.messages`). 일기를 지워도 이건 안 지워진다 |
> | at rest 암호화      | 저장소에서는 안 보인다(DB 설정 · 인프라 쪽) — BE 에 물어야 한다                                 |
>
> **보관 기간 질문의 실제 대상은 마지막 줄이다.** 등급 A(일기 본문·회고 대화)를 기기에서
> 어떻게 눕힐지 정해 놔도, 같은 문장이 서버에 기한 없이 남아 있으면 이 문서가 약속하는
> 것과 사용자가 겪는 것이 달라진다.

> **FE 는 여기에 안을 내지 않는다** — 서버가 무엇을 하는지 모르는 채 쓴 문장은
> 그대로 거짓말이 된다. 답이 오기 전까지 **화면은 서버 쪽에 대해 아무것도
> 약속하지 않는다**(이미 그렇다 — `S1` 의 암호화 문구가 지워진 이유다).

## 6. 이 문서가 열어 주는 것 — MMKV 착수 조건

**5-1·5-2 가 닫히면 바로 시작할 수 있다.** 5-3 은 서버 쪽이라 기기 영속화를
막지 않는다.

착수할 때 함께 들어오는 의존성 둘 — 둘 다 아직 없다:

| 패키지              | 무엇에                                                                    |
| ------------------- | ------------------------------------------------------------------------- |
| `react-native-mmkv` | 통 둘(`enc` · `cache`). 네이티브라 **dev client 재빌드**가 필요하다       |
| `expo-crypto`       | 암호화 키 생성(`getRandomBytesAsync`). `Math.random()` 로 대신하지 않는다 |

붙이는 순서 제안: **① 등급 D(`cache`) 부터** — 키가 필요 없어 위험이 가장 낮고,
`onboardingCompleted` 를 기기에 남기는 것만으로 「앱을 껐다 켜면 온보딩을 다시
본다」의 마지막 흔적이 사라진다. **② 키 배선과 `enc` 통** · **③ 일기·회고 이관**.
