# 모멘토리 화면 QA

## 실행 조건과 범위

- 수정 화면 QA는 `git diff`와 요청 범위를 먼저 확인해 기존 미커밋 작업을 보존한다. 감사만 요청했으면 제품 코드를 수정하지 않는다.
- 화면 계약은 `docs/DESIGN.md`, 관련 `docs/spec/screens/`, 실제 앱 라우트와 공유 뷰에서 확인한다. `expo-lab` 시안이 공유 뷰를 쓰는지 확인하고 Web Mock의 동작을 운영 데이터·기기 동작으로 오인하지 않는다.
- 성능 요청에는 설치된 `vercel-react-native-skills`에서 **관련 규칙만** 읽는다. 일반 권고를 성능 측정 없이 결함으로 판정하거나 새 라이브러리 도입으로 연결하지 않는다.

## 체크리스트

- 상태: 기본·로딩·오류·빈 상태, 권한 거절, 데이터 지연, 긴 한국어와 큰 글씨에서 정보와 복구 경로가 유지되는가?
- 조작: 탭·버튼·선택·되돌리기·화면 이동, 스크롤 위치, 오버레이·바텀시트, 키보드 열림/닫힘과 포커스가 자연스러운가? 연속 탭과 빠른 화면 이동에서 중복 실행이 없는가?
- 화면: 좁은 폭과 큰 글씨, 안전 영역, 하단 탐색, 기기 회전 지원 범위, iOS·Android 차이를 확인한다. 터치 영역·접근성 이름·상태·읽기 순서, 움직임 줄이기 지원을 본다.
- 고정 도크·탭바·오버레이가 있으면 큰 글씨에서 주요 요소의 실제 경계와 클릭 가능 영역이 겹치는지 확인한다. `scrollWidth` 검사나 스냅샷 테스트 통과만으로 겹침이 없다고 판정하지 않는다.
- 회귀: 수정 전후의 핵심 동작과 인접 화면을 비교한다. 테스트는 의미 있는 실패를 잡는 경우에만 추가 제안한다.
- 성능: 실제 느림·잦은 재렌더·긴 목록·큰 이미지·애니메이션 끊김을 재현하고 근거를 남긴다. 정적 코드 패턴만 보았으면 `위험 가능성`으로 표시한다.
- 검증 경로: `npm run typecheck`, `npm run typecheck:expo-lab`, 범위별 Jest, 필요 시 `npm run test:visual`을 사용한다. Expo Web 관찰과 iOS/Android 시뮬레이터·실기기 검증 결과를 분리한다. 시각 회귀 스냅샷은 의도적 디자인 변경과 기존 미커밋 변경을 고려해 해석한다.

## 결과 형식

`검증 환경(웹/시뮬레이터/실기기)`, `범위와 시나리오`, `통과`, `발견 사항(심각도·재현 단계·기대/실제·근거)`, `미검증 및 이유`를 보고한다. 자동 검사 통과를 실기기 통과로 표현하지 않는다. 감사 요청에서는 수정안을 제안하되 적용하지 않는다.

## 사용 예시

- `방금 수정한 홈 화면 QA 해줘. 이번 주 감정 선택과 스크롤 회귀를 봐줘.`
- `프론트 성능 점검해줘. 보관함 긴 목록을 중심으로 측정해줘.`
- `Expo Web과 Android에서 온보딩 키보드 동작을 나눠 검증해줘.`
