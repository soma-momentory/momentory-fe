# 모멘토리 UX 문구

## 실행 조건과 근거

- 사용자가 문구 **검수**를 요청하면 읽기 전용으로 검수한다. 재작성이나 코드 반영을 요청했을 때만 문구를 바꾼다.
- 사용자가 문장 하나를 직접 주고 재작성만 요청하면 **도구 호출 없이** 그 문장과 이 스킬의 톤 기준으로 바로 답한다. 화면·파일을 지정하지 않은 단문 요청에서는 저장소나 디자인 문서를 열지 않는다. 의미가 갈리는 경우에만 필요한 맥락을 짧게 확인한다.
- 화면·흐름의 실제 문구 감사에서는 해당 화면의 `docs/DESIGN.md`, 관련 `docs/spec/screens/`, 실제 UI 문자열의 **해당 부분만** 검색해 확인한다. 두 문서가 충돌하면 `docs/DESIGN.md`가 우선이다. `docs/spec/`은 동결 문서이므로 편집하지 않는다.
- 일반 UX 기준이 더 필요하면 설치된 `ux-writing` 스킬의 `SKILL.md`와 해당 참고 자료를 읽는다. 그 스킬의 영어 문장 길이·독해 학년 수치를 한국어에 기계적으로 적용하지 않는다.
- 명확한 동사, 짧고 구체적인 문장, 사용자가 다음에 할 일을 알 수 있는 안내를 기본으로 삼는다. 토스의 문장 원칙을 참고하되 모멘토리의 차분한 톤과 현재 제품 규칙을 우선한다. 토스 원문을 복제하거나 공식 문구라고 주장하지 않는다.

## 체크리스트

- 위치와 목적: 버튼은 동작을 말하는가, 안내는 필요한 시점에 보이는가, 오류는 원인과 가능한 다음 행동을 정확히 말하는가?
- 한국어: 어색한 번역투, 명사 나열, 불필요한 존대·수식·반복, 띄어쓰기와 조사 오류가 있는가?
- 재작성: 강요를 걷어내더라도 원문의 대상·기능을 유지하는가? `일기`처럼 구체적인 행동을 근거 없이 `마음` 같은 다른 대상으로 바꾸지 않는가?
- 일관성: 오늘·쉼터·보관함·리포트·마이, 기록·일기·회고·감정 등 제품 용어가 같은 뜻으로 쓰이는가?
- 온보딩과 상태: 권한·개인정보·빈 상태·로딩·오류에서 실제 기능이나 결과를 과장하지 않는가? 오류를 훈계하거나 사용자 탓으로 돌리지 않는가?
- AI 회고와 다음 날 편지: 사용자의 감정을 단정하거나 진단하지 않는가? 지나친 위로, 평가, 연속 사용 압박, 행동 강요가 없는가? 사용자가 쓴 사실과 생성 문장을 구분할 수 있는가?
- 접근성: 아이콘만 있는 동작의 접근성 이름, 잘렸을 때의 의미, 화면 낭독 순서가 문구와 맞는가?
- 변경 제안은 실제 표시 길이와 작은 화면에서의 줄바꿈을 고려한다. 원래 의미와 제품 규칙을 보존한다.

## 결과 형식

`위치 | 심각도(높음/보통/낮음) | 현재 문구 | 문제·근거 | 제안 문구` 표로 보고한다. 직접 재작성 요청이면 최종 문구를 먼저 보여 주고 근거를 한두 줄로 적는다. 확인하지 못한 맥락과 사용자 선택이 필요한 문구는 `확인 필요`로 표시한다. 문제가 없으면 범위를 명시하고 통과로 보고한다.

## 사용 예시

- `모멘토리 문구 점검해줘. 온보딩 오류 문구만 읽고 제안해줘.`
- `이 문장을 모멘토리 톤으로 바꿔줘: 오늘도 꼭 일기를 써야 해요.`
- `다음 날 편지의 감정 단정과 과도한 위로를 점검해줘.`
